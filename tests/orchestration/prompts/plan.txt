# Planning a module

Planning a module means writing its design and its next work packages, with their items. The same kind of task plans a
module's next work packages once the ones already planned are nearly built.

[The module's files](/skills/orchestration/planner/references/done-when.md) gives the shape of each file in the module's folder. Builders and
reviewers act on the design and the notes in the plan file, so write them the way the `prompting-agents` skill
describes.

## The design

`DESIGN.md` says what the module's end users need to see, feel or get, and across what range. It names the mechanism
that produces each of those, and says what the module provides to other modules.

Give each behaviour its range from the vision and scope document, and check that its mechanism can produce it
across that range before anyone builds on it. A reviewer will try the edge of any range the design leaves open, and
a range the design never states invites inputs the vision and scope document never meant.

Use only numbers that are real: from the vision and scope document, from the user, or measured. A bound nobody
measured becomes a target builders fail against, so make measuring it the work package's first item, and set the
bound from the result.

## The work packages

Make each work package one outcome a reviewer can judge, small enough for one builder session, which for current models
is hours of work. Each work package costs a builder run, the checks and usually a review, so a finer split pays those
costs again without making the work better. Name each for what someone can see or do once it is Done, such as "A new
end user signs up and lands on an empty dashboard", because that name is what the user reads on the status page.

Write items for the next one or two work packages, the ones you can define well from what is known now, or as far as
your task says. Name the later ones in `PLAN.md` as headings with an ID and an outcome, and no items. When a module
has one planned work package left, the lead starts a planner to write the next ones, and by then the built work has
answered questions you would otherwise guess at.

When the module has been building, read its reviews first. A finding that came up in two reviews becomes an item,
because a builder fixing one review at a time won't stop it coming back. You may change the design, and rename,
merge or drop a named work package the built work has made wrong. If another module's `depends_on` names it, change
that module too.

Under a planned work package in `PLAN.md`, write a note only for what its builder couldn't work out from the items and
the design. Many work packages need none. A note usually says one of these:

- what already exists that the work package builds on, and where it is
- what another module owns that the work package uses or might be tempted to change
- an order the items need, as when one item's measurement sets the bound another item tests

Write it in sentences, with no list of steps, because the builder sees the code close up and plans the work better.

## What it needs from other modules

Write each interface first, so this module can be built against a simple stub that follows the interface until it
needs the real thing. Then, for each thing this module uses from another, find the work package there that delivers it,
and add it, written `"CORE:WP3"`, to the `depends_on` field of the first work package here that can't work without it. If
no work package delivers it yet, add one to the owning module.

- The `plan` command started this session, and it commits and merges the files you leave uncommitted when you end with `PLANNED`.

To finish, end with `PLANNED` once the files are written. The script lists the files you changed itself. If the plan should stay as it is, change no file and end with the `KEEP` line your task gives, if it gives one. If you need an answer the vision and scope document and the files don't give, end with `NEEDS_CONTEXT: <the question>`, and the lead gets it answered. If you can't go on for another reason, end with `BLOCKED: ...`. On `KEEP`, `BLOCKED` or `NEEDS_CONTEXT` the script merges no file of yours.
