Find out why so many milestone reviews in this project failed on a problem that an earlier review of the same milestone could have found. This is a request to do the investigation and write it up, not to discuss it.

Here is why it matters. Between 9 and 11 November, INTEGRATION-ROLLUPS M2, SHARED-UI M2 and SHARED-UI M3 each failed review five to eight times. Most rounds found one or two new problems, and many of those were the same kind of mistake as a problem an earlier round had found. Examples are two paths sharing one pointer target, or one part of the screen still showing the old revision while the rest showed the new one. Each review is meant to be a complete, independent judgement of the milestone, so this pattern means something is wrong. There are two possible explanations, and they lead to different changes in Orchestrate:

1. The problem was already in the code the earlier review judged, and that reviewer missed it. Then the reviews are incomplete.
2. The builder's fix for an earlier problem introduced it. Then the reviews may be fine, and the builders are causing new problems while fixing old ones.

For every Must Fix in a failed review of those three milestones and of SHARED-UI M1, from the second review of each milestone onward, decide which of the two it is. Each claim in the module's `ACCEPTED.json` records the commit its reviewer was given. Settle each case by trying to reproduce the problem at the commit the earliest earlier review judged, and if it isn't there, at the commits in between until you find where it first appears. Reproduce it the way the reviewer did: in the running product where the review used the product, and with a test or a script where that is enough. Pay particular attention to problems reachable only by an indirect route, such as reaching the same view through Search rather than by direct navigation, or through a failed refresh rather than a successful one. Those are the cases most easily missed, by reviewers and by you. A finding you can't settle is "could not tell", with the reason.

For each problem the earlier review missed, read that review's own file and say three things. First, whether the situation that exposes the problem was on the reviewer's list of what it would inspect. Second, whether the review kept examining the milestone after its first Must Fix, or wrote up soon after it. Third, for a review that wasn't the milestone's first, whether it judged the whole milestone again or mainly checked the earlier problems and the new changes. Give how long that review session ran, from the records. Quote the review's words where they show any of this.

Do this in throwaway worktrees checked out at the earlier commits. Leave the module's done-when files, `ACCEPTED.json`, `STATUS.md` and the main checkout alone. Don't run Orchestrate commands that start sessions or change a milestone's state, because this investigation must not move the project. The SHARED-UI M3 builder is paused for the scope change, so don't resume it. If it would be quicker, hand each milestone to its own subagent.

Write the result to `docs/notes/review-completeness.md`, in paragraphs, with one table listing each finding: the milestone, the review round, the finding in a few words, which of the two explanations it is or "could not tell", the commit where it first appears, and how you checked. Lead with the count for each explanation and what you think it means. Keep what you confirmed by reproducing it apart from what you only infer from the review text. Then reply in chat with that summary in under 300 words, so I can pass it on.
