## 1. Long-horizon Codex work: goals, /goal, ExecPlans, AGENTS.md, repo as system of record, harness engineering, mechanical enforcement vs prose

### Takeaway
OpenAI's line has three layers. (a) Durable files in the repo are the memory (spec, plan, runbook, status log; ExecPlans; a short AGENTS.md that points at docs). (b) Since Codex 0.128.0 a native /goal is a "completion contract" with a named verification surface and a blocked-stop condition. (c) Recurring agent mistakes should be turned into lints/tests, not reminders. The measured evidence is thin: the big numbers are single case studies by OpenAI staff.

### Cited Findings
- /goal doc (undated; needs Codex 0.128.0+): a Goal is a persistent, thread-scoped "scoped, user-controlled completion contract". Commands: `/goal <outcome>`, `/goal`, `pause`, `resume`, `clear`. Lifecycle: active, paused, complete, budget-limited. Opinion/design guidance, no measurements. — [Using Goals in Codex](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex.md)
- A good Goal defines six things: outcome, verification surface, constraints, boundaries, iteration policy, blocked stop condition. Template: "/goal <desired end state> verified by <specific evidence> while preserving <constraints>. Use <allowed inputs…>. Between iterations, <how to choose the next action>. If blocked or no valid paths remain, <what to report…>." Weak: "Improve performance". Strong: "Reduce p95 latency below 120 ms on the checkout benchmark while keeping the correctness test suite green". Goal should be "narrow enough to audit but broad enough to allow discovery". — same page
- Goal completion rule: must be backed by evidence (files, commands, tests, benchmark output, artifacts, sources); Codex "should not mark a Goal complete because it seems probably done"; a missed threshold or un-runnable benchmark means not complete. The model can start a Goal and mark it complete; pause/resume/clear/budget-limit remain with user or system. Budget-limit is not completion. — same page
- Goal runtime: continues only when thread idle, goal active and in budget, nothing else pending; plan-only turns do not trigger continuation; a continuation turn with no tool call suppresses the next automatic continuation (anti-spin). Goal doc says it works best with a "durable objective, an evidence-based finish line, and a path that may take several turns". Page gives no token amounts. — same page
- Goals doc says: do not use for one-line edits, vague finish lines ("Make this better"), and "Do not use a Goal to hide uncertainty" (state flaky results, proxy evidence). It explicitly names research/benchmark/flaky-test work as the fit; it does not say anything about subjective/creative deliverables. — same page
- Long-horizon blog (undated; mentions GPT-5.3-Codex, so early 2026): one run ~25 hours, ~13M tokens, ~30k lines, GPT-5.3-Codex at "Extra High", building a design tool from a blank repo. Author says "not perfect or production-ready". This is one anecdote by an OpenAI staffer, not a benchmark. — [Run long horizon tasks with Codex](https://developers.openai.com/blog/run-long-horizon-tasks-with-codex.md) and [cookbook example](https://developers.openai.com/cookbook/examples/codex/long_horizon_tasks/)
- The same post's four-file "durable project memory" stack: Prompt.md (goals, non-goals, hard constraints, deliverables, "done when"), Plan.md (milestones small enough to finish in one loop, each with acceptance criteria and validation commands, plus a "stop-and-fix" rule and decision notes to prevent oscillation), Implement.md (runbook: plan is source of truth, validate after every milestone, keep diffs scoped), Documentation.md (status/audit log). Verification after each milestone: tests, lint, typecheck, build, export; fix before advancing. Humans review at milestones. Quote: "agentic coding is increasingly about time horizon, not just one-shot intelligence". — same
- ExecPlans / PLANS.md cookbook (Sept-Oct 2025 vintage; page now marked "archived" and may reference outdated models; recommends gpt-5.2-codex): AGENTS.md gets an "ExecPlans" section saying to use one for complex features or significant refactors; plan is "fully self-contained", a "living document", must yield "demonstrably working behavior, not just code changes". Mandatory sections: Progress (only checklist section, timestamped), Surprises & Discoveries, Decision Log, Outcomes & Retrospective; skeleton also has Validation and Acceptance, Idempotence and Recovery. Rules for the agent: do not ask the user for "next steps", resolve ambiguity and record it, commit frequently. Acceptance phrased as human-checkable behaviour (example: HTTP 200 from a health endpoint). Claim that a similar PLANS.md let Codex work "for more than seven hours from a single prompt" (unmeasured anecdote). Notes "ExecPlan" is an arbitrary term Codex was not trained on. — [Using PLANS.md for multi-hour problem solving](https://developers.openai.com/cookbook/articles/codex_exec_plans.md)
- Best-practices page (undated, current; GPT-6 era): prompt = goal, context, constraints, "what 'done' looks like"; start in Plan mode (`/plan`) for complex or ambiguous work; for long multi-step work "use a PLANS.md or execution-plan template" (still recommended in 2026, alongside goals elsewhere; the page itself does not mention goals). AGENTS.md: "open-format README for agents"; repo layout, run/build/test/lint commands, conventions, do-not rules, how to verify; layered (global, repo, subdirectory, closest wins); "Keep it short"; after a repeated mistake ask Codex for a retrospective and update the file; point to task-specific markdown (planning, review, architecture) for large guidance. Common mistakes list: durable rules in prompts instead of AGENTS.md/skills; not telling the agent how to run builds/tests; skipping planning; one chat for the whole project; scheduling before manual reliability. — [Codex best practices](https://learn.chatgpt.com/docs/learn/best-practices)
- Harness engineering (OpenAI post, Ryan Lopopolo, 2026-02-11; primary page 403, figures below are as reported by secondaries, treat as reported not verified): five months, empty repo from late Aug 2025, zero hand-written code, ~1M lines, ~1,500 merged PRs, team of 3 growing to 7, ~3.5 PRs/engineer/day; single Codex runs often over 6 hours. — summary at [yage.ai survey](https://yage.ai/share/harness-engineering-survey-en-20260312.html), corroborated by [The Neuron](https://www.theneuron.ai/explainer-articles/openais-harness-engineering-playbook-how-to-ship-1m-lines-of-code-without-writing-any/), primary at [openai.com/index/harness-engineering](https://openai.com/index/harness-engineering/) (not read)
- Repository as system of record: quote (via The Neuron) "From the agent's point of view, anything it can't access in-context while running effectively doesn't exist." Decisions living in Slack or heads were invisible; an agent used the wrong package until the decision was written into the repo. — The Neuron
- AGENTS.md as a map: one big instruction file failed because context is scarce and it crowds out the task; the replacement is ~100 lines acting as a table of contents to a structured `docs/` (design docs, execution plans, architecture decisions, quality scores). — yage.ai survey; The Neuron
- Mechanical enforcement over prose: strict layered architecture (Types, Config, Repo, Service, Runtime, UI) with dependency directions enforced by custom linters that Codex wrote; linter error messages carry remediation text for the agent; example: a custom ESLint rule banning a duplicated helper outside the telemetry-wired location, written by Codex with 100% test coverage. Lopopolo (Build Hour, via The Neuron): "It's super easy to add leverage to your codebase by vibing up some new lints." — yage.ai survey; The Neuron
- Observability for agents: Chrome DevTools Protocol wired in for screenshots and UI-flow driving; per-worktree logs/metrics/traces queryable with LogQL/PromQL. — yage.ai survey (as reported from OpenAI post)
- Entropy control: team first spent ~20% of Fridays cleaning "AI slop" (The Neuron says "every Friday"), which did not scale; replaced by recurring background Codex tasks that scan for deviations from encoded "golden principles", update quality scores and open small fix PRs, mostly reviewable in about a minute. — yage.ai survey; The Neuron
- Merge philosophy: minimally blocking merge gates, short PR lifetimes, flaky tests handled by follow-up runs; the post itself reportedly says this would be irresponsible at low throughput and is right only when agent output exceeds human review capacity. OpenAI says it does not yet know how architectural consistency evolves over years in a fully agent-built system. Greenfield only. — yage.ai survey
- Late-2026 revision on prose vs instructions (GPT-6 Astra, 2026-09-11, Eric Provencher): "Regularly ask whether each instruction is still needed"; older models needed prompting to run tests and Astra runs them itself, so testing instructions can cause unnecessary runs; "Ask first" boundaries written for older models may make Astra stop work it could safely continue; Astra "may stop early" so define completion before starting; progressive disclosure, root skill/doc as "minimal router"; drop step-by-step recipes because "over-specific guidance can now hurt". No measurements. — [Rethinking skills and prompts for GPT-6 Astra](https://learn.chatgpt.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)

### Inferences
- The durable pattern across Feb to Sep 2026 is: outcomes and checkable evidence in files; procedure shrinks as models improve. A framework that writes machine-checkable done criteria is in line with the /goal template ("verified by <specific evidence>") and the Plan.md "acceptance criteria and validation commands".
- OpenAI's evidence for mechanical enforcement is qualitative (one team, one greenfield repo) and the primary text was not accessible; the "lints are cheapest leverage" claim is opinion from the practitioners.
- Nothing I found from OpenAI says how to set done criteria for subjective work in /goal; the Goals doc's examples are all measurable.

### Gaps
- Could not read the primary Harness Engineering post (403); all its figures are second-hand. No later OpenAI revision of that post found.
- Goals page and long-horizon blog have no publication dates; the "Long-running work" docs page was linked but not retrieved. Token-budget configuration is not specified on the Goals page.

## 2. Subagents, multi-agent orchestration, handoffs, context inheritance, review agents, parallel work and worktrees

### Takeaway
OpenAI's current Codex docs favour subagents for read-heavy, independent work (exploration, tests, triage, review) and warn about parallel writes and token cost. Reviewers are cast as narrow read-only agents. Instruction-level "do not edit" is explicitly not enforcement; sandbox is.

### Cited Findings
- Subagents doc (undated, current; subagents enabled by default in app/CLI/IDE): good fit is "read-heavy, independent work such as exploration, tests, triage, and summarization"; "more caution" for parallel write-heavy work because of conflicts and coordination overhead; benefit is keeping noisy output off the main thread ("context pollution", "context rot"), returning summaries. Spawned only on explicit request or when AGENTS.md/skills ask. Good prompts say how to divide work, whether to wait for all agents, what summary to return. "Subagent workflows consume more tokens than comparable single-agent runs". — [Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents.md) (old URL developers.openai.com/codex/subagents redirects here)
- Context inheritance: subagents inherit parent's provider, permissions, MCP servers, skills; service tier follows the root session; model and effort default to parent's (spawn value, then `[agents]` default, then parent). The page does not say how much conversation a child receives. Sandbox and approval policy are inherited and cannot be overridden per agent; "Instructions aren't enforcement". Non-interactive runs fail on actions needing new approval. — same page
- Config: `agents.enabled`, `agents.max_concurrent_threads_per_session` (`max_threads` legacy alias), `agents.default_subagent_model`, `agents.default_subagent_reasoning_effort`; built-ins `default`, `worker`, `explorer`; custom agents are TOML in `.codex/agents/` or `~/.codex/agents/` with required `name`, `description`, `developer_instructions`. `max_depth` not mentioned on the page. — same page
- Review pattern in the doc: three narrow agents: `pr_explorer` (maps paths, read-only), `reviewer` (correctness, security, test risks, read-only), `docs_researcher`; example reviewer uses `model_reasoning_effort = "medium"`, "Do not edit files. Lead with concrete findings." The doc also lists `high` effort as suited to "reviewers". Parallel-review prompt: one subagent each for security, test gaps, maintainability; wait for all; summarise by category. Frontend debug pattern: `code_mapper`, `browser_debugger` (reproduce and capture evidence), `ui_fixer` (smallest fix after failure understood). — same page
- Best practices: offload bounded work (exploration, tests, triage) to subagents to keep the main agent on the core problem; worktrees let live tasks run without touching the same files; "Running live tasks on the same files without worktrees" is a listed mistake; keep one chat per coherent unit, fork only when work branches. — [Best practices](https://learn.chatgpt.com/docs/learn/best-practices)
- Worktrees: by default Codex keeps the 15 most recent Codex-managed worktrees (reported in search snippet of the official worktrees doc; page not fetched, redirected to learn.chatgpt.com/docs/environments/git-worktrees). — [Worktrees](https://developers.openai.com/codex/app/worktrees)
- GPT-6 guidance: "Delegate to subagents when work can run in parallel, and specify when and how much to delegate." — [Latest model guide](https://developers.openai.com/api/docs/guides/latest-model.md)
- Recent changelog (CLI 0.166.0 and 0.167.0, 2026-10-29 and 2026-11-06): Guardian review routes state-changing multi-agent calls (#57451); synchronous Guardian review opt-in for native tool calls; subagent picker lists pending approvals first; host-managed child startup can expose the parent's context (#58390); "goal provenance" tests in Guardian reviews. These are release notes, not guidance, and the snippets were truncated. — [Changelog](https://learn.chatgpt.com/docs/changelog?date=2026-10-15)
- Handoffs vs agents-as-tools in the Agents SDK: I found only third-party statements ("if the specialist owns the answer, handoff; if the manager owns the answer, tool"; handoff recipient sees prior conversation unless an input filter trims it; start with one agent). Not verified against OpenAI's docs. — [search results, third-party only](https://towardsdatascience.com/build-multi-agent-apps-with-openais-agent-sdk/)
- Agents SDK team's own use (reported by yage.ai from a 2026-03-09 OpenAI post by Kazuhiro Sera): merged PRs rose 316 to 457 over three months; Codex review as a required path. Second-hand. — yage.ai survey

### Inferences
- OpenAI gives no evidence that multi-agent beats single-agent for write-heavy work; its stated advantage is context hygiene, its stated cost is more tokens. A fresh-context reviewer is supported as a read-only agent pattern, but the doc offers no measurement of review quality.
- A reviewer subagent inherits the parent's sandbox, so true read-only review requires the parent session to be read-only; the doc's "do not edit" text is not enough.

### Gaps
- No official Agents SDK docs page was fetched; handoff and context-filter guidance is unverified. No OpenAI statement found on when NOT to split beyond "read-heavy good, parallel writes careful". No published measurements of subagent benefit.

## 3. Prompting current GPT models for agentic work

### Takeaway
Direction since mid-2026 is outcome-first, lean prompts: state target, success criteria, constraints, evidence needed; let the model pick the route; prune older procedure and re-test. Evidence is mostly OpenAI's own assertions; one report of internal ablations showing "directional improvements" is second-hand.

### Cited Findings
- GPT-6 Astra prompt guidance (2026-09-11): see section 1 (trim AGENTS.md and skills, define completion up front, grant explicit permission for known-safe workflows with example "The local tests use disposable fixtures and have no production access.", requirement to stop for review after first implementation pulls the model toward early stopping). The article does not cover effort, verbosity or numbers. — [Rethinking skills and prompts](https://learn.chatgpt.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)
- Latest-model guide (undated; models gpt-6-astra, gpt-6.1-sol, gpt-6.1-terra, gpt-6-luna): persist "until the user's intended goal is complete", bias toward action, avoid stopping at a plan; pause only before irreversible or destructive actions; Astra "tends toward detailed, formatted responses with lists, tables, and Markdown", so specify concise style if wanted; Astra tests thoroughly, may over-test small tasks; "User instructions take precedence over skill guidance. Audit skills and files such as AGENTS.md, since Astra is sensitive to them." — [Latest model guide](https://developers.openai.com/api/docs/guides/latest-model.md)
- GPT-5.5 / 5.6 prompt guidance (mid-2026, secondary coverage only; OpenAI Model guidance page said to be updated 2026-07-22; one source says 5.6 guide published 2026-07-09): define outcome, success criteria, constraints and context, then let the model choose the path; remove route descriptions group by group on a test set, restore any whose removal regresses quality; reported warning that conflicting rules cause more instability than missing detail; reported OpenAI internal ablations "directional improvements", workload-dependent. Contrast: GPT-4.1 (April 2025) SWE-bench prompt hard-coded an eight-step workflow. I could not read the primary text. — [yage.ai summary, 2026-07-24](https://yage.ai/share/gpt56-prompt-guidance-result-certainty-en-20260724.html); [cryptobriefing](https://cryptobriefing.com/openai-gpt-56-prompting-guide-outcome-first/)
- Best practices (current): four-part prompt (goal, context, constraints, done). — [Best practices](https://learn.chatgpt.com/docs/learn/best-practices)
- Codex 0.161.0 (2026-10-07): GPT-6.1 Sol became the default model. — [Changelog](https://learn.chatgpt.com/docs/changelog?date=2026-10-15)

### Inferences
- Over-specified procedural skills/AGENTS.md written for earlier models are explicitly called out by OpenAI as potentially harmful on Astra. A framework that prescribes step-by-step builder procedure is the kind of thing this guidance says to test for removal. The guidance still endorses specifying done criteria, verification evidence and permission boundaries.
- The guidance is model-specific and moves roughly every 2 to 3 months; a framework should treat it as per-model, not permanent.

### Gaps
- Primary 5.5/5.6 guide text not read. No OpenAI statement found on verbosity controls beyond "specify the style". No measured over-instruction penalty published.

## 4. Verification, self-review, evals, graders; output with no objective test

### Takeaway
OpenAI's published verification stance is "evidence over feeling": tests/lint/build per milestone, completion backed by artifacts, and for skills a layered eval (deterministic JSONL trace checks then a model-graded rubric). I found no OpenAI material on judging games or 3D assets.

### Cited Findings
- Skills eval post (dated by search as Jan 2026; page undated): four categories of success (outcome, process, style, efficiency), keep the must-pass list small; 10 to 20 prompts per skill including negative cases; deterministic checks from `codex exec --json` traces (commands run, files exist, command count, token usage); then a read-only `codex exec` with `--output-schema` returning JSON `overall_pass`, `score` 0-100, `checks[{id,pass,notes}]` for style judgments (e.g. functional components, Tailwind utilities, no extra UI libraries). Adds suggested runtime smoke tests (`npm run dev` responds to curl/Playwright). Quote: instead of "does this feel better?" evals ask concrete questions. No pass rates reported. The rubric examples are structural/style rules, not aesthetic judgment. — [Testing Agent Skills Systematically with Evals](https://developers.openai.com/blog/eval-skills.md)
- Best practices: have Codex write or update tests, run relevant checks, confirm behaviour and review the diff; `/review` against base branch, uncommitted changes, commit, or custom instructions; `code_review.md` referenced from AGENTS.md; automatic GitHub PR review or @Codex. — [Best practices](https://learn.chatgpt.com/docs/learn/best-practices)
- Self-review then agent reviewers until all are satisfied; humans shift to defining standards and encoding taste (harness post, reported). Code-review scale claim: >100,000 external PRs/day with >80% of comments receiving positive reactions (reported by yage.ai from another OpenAI article; unread). — yage.ai survey
- Latest-model guide: run tests suited to the change, broaden only on new failures; do not write tests for reversible low-impact changes that mirror the implementation. — [Latest model guide](https://developers.openai.com/api/docs/guides/latest-model.md)
- Goals: completion requires evidence; a "final report separating reproduced mechanics, approximate results, blocked exact replay, and remaining uncertainty" is the doc's example for a research task with imperfect evidence. — Goals doc
- Third-party only (not OpenAI): rubric graders show length/style bias and inconsistent scores; calibrate or ensemble. — [search summary](https://developers.openai.com/blog/eval-skills)

### Inferences
- The closest OpenAI-endorsed method for subjective output is a read-only structured-output rubric grader with a small must-pass list plus deterministic runtime checks; nothing says it is validated against human judgment.
- "Fresh-context reviewer" is consistent with OpenAI's read-only reviewer subagents and with the self-then-agent review loop, but OpenAI publishes no comparison of independent versus self-review.

### Gaps
- No OpenAI material found on visual/gameplay/3D verification, human-in-loop gates for taste, or grader calibration. Computer-use / browser-driving appears in OpenAI changelog coverage but I did not read primary guidance on it for verification.

## 5. Cost: model and effort per task, quota, caching, cloud vs local

### Takeaway
OpenAI says: start at the default effort, move up only when quality gain justifies time and tokens; use cheaper models for narrow high-volume work; subagents and goals cost more tokens. Official numeric quota/caching figures were not found.

### Cited Findings
- Best practices: Sol at default effort; Luna starts at High, Astra at Light (`low`); Low for fast scoped tasks, Medium/High for complex changes or debugging, Extra High for long reasoning-heavy work. — [Best practices](https://learn.chatgpt.com/docs/learn/best-practices)
- Subagent doc: `gpt-6.1-sol` for demanding multi-step work; `gpt-6-luna` for "fast, narrow, high-volume work"; effort `high` for reviewers, `low` for simple speed-critical tasks; "Higher effort increases response time and token usage"; subagents use more tokens than single-agent runs; per-agent `model` and `model_reasoning_effort` settable. — [Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents.md)
- API guide: Sol supports low/medium(default)/high/xhigh/max; Terra none to max, "Start at `medium` and increase only if the quality gain justifies the time and tokens"; change effort mid-conversation with a `configuration_update` item and leave request-level `reasoning.effort` unchanged "to preserve caching". Third-party guide: "Do not automatically use the highest effort" (not primary). — [Latest model guide](https://developers.openai.com/api/docs/guides/latest-model.md)
- Changelog: reasoning-token accounting preserved across resume and fork to avoid premature compaction (2026-10-29); dollar-based thread usage shown for ENT26 plans; GPT-5.5 retired from Codex 2026-10-14; Sol default from 0.161.0. Release notes, not guidance. — [Changelog](https://learn.chatgpt.com/docs/changelog?date=2026-10-15)
- Goals: budget-limited state exists; stops substantive work at budget; no amounts given. — Goals doc
- Cloud vs local: best-practices page says almost nothing on Codex Cloud beyond PR review; worktrees isolate local parallel tasks; automations can run in a dedicated worktree or local environment. — Best practices
- Third-party, unverified: cached input about 10% of regular rate; $100-$200 typical monthly cost; 5-hour and weekly usage windows. — [search summary](https://codex.danielvaughan.com/2026/05/07/codex-cli-goal-command-persisted-long-horizon-workflows-pause-resume-budget/)

### Inferences
- OpenAI's cost advice is: tier effort by task and keep prompts stable for caching; its docs give no evidence on cost per quality point for multi-agent vs single-agent.

### Gaps
- No official pricing, quota, caching-discount, or cloud-vs-local cost guidance retrieved.

## 6. What changed in 2026 vs 2025 (dated)

- 2025-08/09 (GPT-5, GPT-5-Codex): prompts add persistence and exploration/stopping boundaries; PLANS.md/ExecPlans for 7-hour runs (cookbook, now "archived"). Per yage.ai summary of August 2025 guidance. 2025-04 GPT-4.1 prompts hard-coded workflows.
- 2026-01: skills eval method (codex exec JSONL + rubric). Date from search result, page undated.
- 2026-02-11: Harness engineering post; AGENTS.md shrinks to ~100-line map; lints and golden-principle cleanup agents.
- 2026 early (GPT-5.3-Codex): 25-hour, 13M-token run with prompt/plan/implement/documentation file stack (replaces single ExecPlan with four files; similar spirit).
- ~2026-03: subagents and custom agents reach GA per third-party; now on by default.
- ~2026-05 (Codex 0.128.0): native /goal.
- 2026-07: outcome-first 5.6 guidance (secondary).
- 2026-09-11: Astra guidance: trim instructions, remove older-model testing/ask-first rules.
- 2026-10-07: GPT-6.1 Sol default; 2026-10-14 GPT-5.5 retired in Codex.
- 2026-10/11: Guardian review of multi-agent state-changing calls (safety layer, not delivery guidance).
- Net shift (inference from the above): from "specify the procedure and a big rules file" toward "specify outcome, evidence and boundaries; keep rules in lints/tests; prune instructions per model". Plans remain recommended for long work; goals add a native loop.
