# Pattern 3: teaching what a capable model already knows

Scope: every file under `skills/orchestration/` (skills, stages, tasks, references, prompts, README, GLOSSARY) and the
agent-facing text in `agent_loop.py` (`session_rule`, `resources_rule`, `needs_rules`, `handoff_note`, the run
REFUSED `why`, `COMMAND_HELP` for `run`, `merge`, `lock`, `check`), plus the saved prompts in
`tests/orchestration/prompts/`. `lead/stages/4-build.md` ignored as instructed.

## Overall

The set is already mostly clear of this pattern. Most of what reads like general advice turns out, on a closer look,
to be one of three things a capable model couldn't guess: an orchestrate mechanic (who owns which field, what the
script reruns, what a fresh reviewer sees), a limit of agents in this setup (no live video, sandboxed browsers,
headless sessions), or the user's own preference (dialogue mapping, numbered questions, no default for a number the
project turns on, items that say what and never how). Lines like that stay.

The agent-facing text in `agent_loop.py` is clean. Each rule I read there is backed in its docstring by something
that happened in Thrum: a builder treated a held lock as a fault, a headless session tried Computer Use, a builder
asked a question through a tool and waited. I found nothing there to cut for this pattern.

The README and GLOSSARY are written for people. Definitions there such as **Agent**, **Subagent** and **Worktree**
(GLOSSARY.md 30-35, 65-66, 185-190) belong in a glossary for human readers, so they are outside this pattern.

What's left is about 40 lines, mostly in three places: general testing practice in `planner/references/proofs.md`;
general advice on writing for a reader, said three times in the builder skill and twice in the reviewer skill; and
explanations of how git, merges and locks work in the builder skill, which `--help` already covers.

## 1. General test practice in `planner/references/proofs.md` (about 12 lines)

### 1a. The "Kinds to start from" table teaches test design (proofs.md 30-48)

> | Automated test | `check` | The behaviour, and a command that tests it end to end | It tests a mock, or only the easy path |
> | Property or fuzz test | ... | The inputs miss the cases that happen in real use |
> | Golden output | ... | The golden file was made by the code under test, and nobody checked it |
> | Determinism | ... | It compares a run only with itself in one process, or ignores timing and threads |

**What's wrong.** The rows for automated, property, golden-output and determinism tests, and their "too weak if"
cells, are textbook test design. A planner running on Opus 5.5 or GPT-6.2 knows that a test against a mock is weak and
that a golden file made by the code under test proves nothing. It's also a menu of things the agent can do, which the
user said the skills shouldn't be.

**What's particular, and stays:**
- the `inspect` rows (visual quality, 2D image, 3D asset, motion, user journey), because their "what to write" cells
  carry what agents in particular get wrong: crops at full resolution, several angles, a sequence of frames rather
  than video, and screenshots from the exact build;
- the "options to choose from" row, which ties to `needs: human_feedback`;
- the code-or-interface `ask` row;
- the benchmark row, because it points to the cost section's rule that a number comes from the brief or a baseline.

**Fix.** Delete the automated, property, golden-output and determinism rows (4 lines). Rename the section to something
like "Inspections, by what is inspected", and keep the line saying a project can add its own kinds in a guidance file.

**Checked:** `plan --help` and the planner prompt add no text about kinds of test, so nothing else depends on these
rows.

### 1b. "One proof often isn't enough", with a worked example (proofs.md 26-28)

> Often one proof isn't enough, because each kind misses different things. Take a ball bouncing in a physics game. ...

**What's wrong.** It explains defence in depth, which the model knows. Line 17 ("names one or more proofs, and passes
only when each of them passes") and planner/SKILL.md 89 ("Many items need more than one...") already make the point
that matters to orchestrate.

**Fix.** Delete lines 26-28.

### 1c. "How to inspect" explains what a checklist is for (proofs.md 113-116, 122-123)

> Work down it line by line, because a reader without a list looks at whatever catches its eye and misses the broken parts.
> Answer each line in the review or with the evidence, so anyone can see what was looked at and what wasn't. If the
> checklist misses a part of the work you can see is wrong, report that too.

**What's wrong.** Explaining why you use a checklist, and that a reviewer should also report a fault the checklist
missed, is general practice. reviewer/tasks/milestone.md 34-37 already says to answer each line yes or no.

**What's particular, and stays:** crops at full resolution, the reference beside the work rather than recalled from
memory, the edge conditions from the settings (118-120), and the agent-perception paragraph (125-127).

**Fix.** Cut 113-123 to: "An `inspect` item is a checklist the planner wrote from the milestone's reference. Answer
each line in the views and conditions it names (the table above gives them for each kind), with crops at full
resolution, the settings' edge conditions for the target, and the reference open beside the work." About 4 lines
go.

### 1d. The cost-benefit opening of "What a proof costs" (proofs.md 52-54, 72-73)

> A proof is worth what it catches, set against what it costs, and both depend on how the build runs, not only on the item.
> Weigh each proof's catch against its cost in time and in queueing for the builders who share its resource.

**What's wrong.** That a check should be worth its cost is general practice, and the section says it twice. What
follows it is the particular part: checks rerun on main, serial locks across ten builders, `reads`, `gpu.alone`, the
test command capping merges per hour.

**Fix.** Delete 52-53 up to "Most proofs are cheap, so this rarely decides anything." and keep "It decides a lot
when a proof is slow, needs a resource one run at a time may use, or needs the user." Delete line 72. Keep 73-74
(past reviews show which proofs found real faults). About 3 lines go.

## 2. Advice on writing for a reader, repeated in builder and reviewer (about 9 lines)

All of these say "write for a reader who wasn't in your session, and separate what you verified from what you
suspect". The `prompting-agents` skill already covers that, and each file points to it anyway. Fix them together:
keep one pointer to `prompting-agents` per skill, and keep only the orchestrate-specific instruction.

### 2a. builder/SKILL.md 98-103, "What you write"

> Write them the way the `prompting-agents` skill describes. ... Say which things you confirmed by running something and
> which you only suspect, because the lead acts on your report as written.

The "verified vs suspect" point is already at line 57 (the LOG entry). **What's particular, and stays:** name an item
by its ID and a few words, and a module by its plan name, because the lead knows the plan's names but not the code's;
and what other builders should do is the lead's call. **Fix:** "Write your last line, handoff and log entry as the
`prompting-agents` skill describes. Name an item by its ID and a few words ("M2.5, the window resize recording") and a
module by its name in the plans, because the lead knows the plan's names, not yours or the code's. What other
builders should do is the lead's to decide." About 2 lines go.

### 2b. builder/SKILL.md 87-89 and 91-93, how to write a question and a handoff

> so write it to be answered without your session: what you need, the choices you see, and which you would pick and why.
> Whoever picks the milestone up, a builder or a planner, has seen none of your session, so write it for them.

**What's wrong.** It teaches how to ask a good question and how to write a handoff for a cold reader. **What's
particular, and stays:** the lead routes the question; the script names the handoff in the next prompt, so the last
line can be short; and rewrite an earlier handoff rather than add to it. **Fix:** cut 88-89 to "The lead answers it,
gives it to a planner or takes it to the user." Cut 91-93 to "If you stop without `DONE`, first write a handoff where
your prompt says; the script names it in the next agent's prompt, so your last line can be one sentence." About 2
lines go.

### 2c. reviewer/SKILL.md 55-60, "Writing findings"

> Write each finding for an agent who saw none of your session and will take it as everything you know ... Put the worst
> finding first. Mark each Must Fix or Suggestion, and say whether you verified it or only suspect it. Write the review
> the way the `prompting-agents` skill describes.

**Fix:** one sentence: "Write the review as the `prompting-agents` skill describes: worst finding first, each marked
Must Fix or Suggestion and verified or suspected, with what you tried and what you left untried." About 3 lines go.

### 2d. reviewer/SKILL.md 68-69, keeping the session small

> Everything you look at stays in your session, so judge a recording from a few still frames and read the end of a log
> rather than the whole file.

**What's wrong.** Managing context is general agent practice. **Fix:** delete that sentence and keep the
`background`/`wait` sentence, which is orchestrate's. Rename the section "Long commands". About 1 line goes.

## 3. How git, merging and locks work, in the builder skill (about 6 lines)

### 3a. builder/SKILL.md 134-136, how `merge` works

> `merge --worktree .` rebases your branch onto the main branch, runs the test command, and merges. It is the only way
> to bring work into the main branch, because every other builder's worktree is built on that branch's history.

**What's wrong.** The reason ("every other builder's worktree is built on that branch's history") explains git. The
mechanics (rebase, test, batch) are in `merge --help`, which I checked: it covers rebase, test, batching, splitting
a failed batch in halves, `conflicts` and `main_broken`. **Fix:** "Bring work into the main branch only with
`merge --worktree .`, so it is tested with everyone else's; when several builders merge at once it tests them as a
batch, so it can take a while." About 1 line goes.

### 3b. builder/SKILL.md 146-151, lock etiquette

> hold the lock only for the command that needs it, because every other builder that needs the resource waits while you
> hold it. ... `locks` shows who holds each lock, so do other work while you wait

**What's wrong.** Holding a lock no longer than needed is basic concurrency. `resources_rule()` already puts this in
the prompt ("hold one only for the part of the work that needs the resource"), together with the hold limit, and
`lock --help` explains queueing and the 30-minute stop. **What's particular, and stays:** check the user is there and
the screen is unlocked before you take a lock for a run that needs them; and a busy resource is normal, not a fault
(Thrum showed a builder reporting one as a fault, per `resources_rule`'s docstring). **Fix:** "Wrap a command that
uses one of the project's resources in `lock <name> -- <command>`. Before you take a lock for a run that needs the
user or the screen, check they are there. A busy resource is normal: do other work, and end `BLOCKED` only if the
holder seems stuck, naming it." About 2 lines go.

### 3c. Scope discipline (builder/SKILL.md 176-177; lead/SKILL.md 75)

> Change only what you were asked to. Mention anything else you notice in your reply, because it may belong to a module another builder is working on.
> Undo a commit with `git revert`, which adds one.

**What's wrong.** "Change only what you were asked to" is basic practice, and lines 37-38 already say "is that
change and nothing more". ", which adds one" explains git. **Fix:** in the builder, keep only "Mention anything else
you notice, because it may belong to a module another builder is working on." In the lead, cut it to "Undo a commit
with `git revert`." About 1 line goes.

## Looked at and kept

- lead/stages/1-interview.md, apart from the two lines above: the goal asked first with no recommendation, numbered
  questions never reused, no default proposed for a number the project turns on, joining the dots between rounds,
  pinning the pre-mortem to numbers or shipped examples, and the brief's headings. Each is the user's preference or an
  orchestrate need, not general interviewing.
- planner/references/done-when.md: all of it is schema, ownership and script behaviour.
- builder/SKILL.md 116-130 (repo-root evidence paths, recapturing after a merge, proof scripts kept in the repo
  because checks run in a clean checkout, `main-check`): all orchestrate mechanics.
- lead/SKILL.md 37-38 ("Let each command's output and exit status reach you ... a refused command line looks like
  success once its error is thrown away"): reads like shell basics, but it guards against a lead piping results into
  `tail`. Kept, with low confidence.
- The Codex note in `session_rule()` (`yield_time_ms`, `apply_patch`, `ps` refused, browser outside the sandbox):
  quirks of the host, not general knowledge.
- reviewer/references/graded-examples.md: calibrations of the user's strictness, not teaching.
