# Pattern 4: procedures where a goal belongs (and judgement handed to a rule)

Scope: every file under `skills/orchestration/` except `lead/stages/4-build.md`, plus the agent-facing strings in
`lead/scripts/agent_loop.py` and the saved prompts in `tests/orchestration/prompts/`. Read-only; nothing edited.

Overall: the planner and reviewer files are mostly in good shape. They state outcomes and reasons and leave the
route to the agent. The procedures sit mainly in lead stages 1 to 3, in the builder's "Without a lead" section, and
in a few `next`/`why` strings. The opposite failure, where judgement is handed to a rule or to someone else, shows up
in two clear places: the reviewer on permissions, and `model_next` sending a mundane rerun to the user.

Rough total: about 60 to 70 lines would go from the skill files, two script strings would be rewritten, and about
3 lines would be added to the reviewer.

---

## 1. Lead stage 2, "The project settings": a line-by-line recipe for the template (whole section)

`lead/stages/2-start-planning.md:6-34`. Quotes: "Keep the template's `Worktrees:` line ... and its `Graded examples:`
line", "write `- **Test command:** none  *(the planner chooses it)*` until then", "Leave out each host and model line
the user named nothing for", "Write `Review host: other` when the user builds with both hosts", "Leave out the
`Builders:` line until they have seen the plan".

**What's wrong.** Most of this section is moves, one per settings line, explaining how each line behaves. That
belongs to the template. `settings --template` already gives each line a `*(script: ...)*` note saying what it does
(checked: `agent_loop.py:10126-10165`; the Worktrees, Graded examples, Test command, Builders and Review host notes
all spell out the behaviour). Two of the moves exist only because the template's defaults are wrong for a new
project:

- The template's Test command is `npm run check` (line 10128), so the stage has to tell the lead to swap in `none`.
- The template carries a placeholder `Builders:` line (line 10133), so the stage has to tell the lead to remove it.

**Fix.** Have the script do the mechanical part. Make the template's defaults right for a new project: `Test
command: none *(the planner chooses it)*`, and no `Builders:` line (or one commented out). Keep `Worktrees:` and
`Graded examples:` as they are, and move the "leave out host/model lines so defaults track new models" reason and the
`Review host: other` reason into those lines' notes. Cut the section to its goal and mandate. Gist:

> You write `ORCHESTRATE.md` from `settings --template` and the brief, because you know the brief best: the purpose,
> the quality bar, the targets, and what is out of bounds. Write how the user wants the agents to work, from what they
> have said, and ask in their words for the rest. Choose what they can't, and tell them. Only the user's words grant a
> permission, so write `Merge: push` only if they allowed pushing (and say in its note that it is the authorisation
> an `AGENTS.md` asks for), and write `Human decides` in their words.

**Checked:** template text at `agent_loop.py:10120-10170`; `run` refuses with no Builders count (line 8030).
**Lines:** about 10 go.

## 2. Lead stage 1, "Map the dialogue": an interview script rather than an outcome (whole section)

`lead/stages/1-interview.md:57-87`. Quotes: "Run the interview as dialogue mapping, with the brief's sections as the
root questions.", "Settle the scope: ...", "Run a pre-mortem on the first release. Pin each answer to a number ...".

**What's wrong.** The goal is already stated well in "When you're done" (lines 36-41): a brief the planner can plan
from without working around a hole, at no more depth than that. "Map the dialogue" then lays out the moves in
order: name the method, ask the goal first, run numbered rounds, give the cost of each choice, join the dots between
rounds, settle scope, run a pre-mortem. A capable model knows how to interview. The moves worth keeping are the ones
with a reason the model wouldn't otherwise act on:

- ask the goal open, because options hide the reason;
- number the questions, so answers come back fast;
- give each choice's cost with a recommendation, because the user can't weigh a cost they can't see;
- state the inferences for the user to overturn, and make bigger jumps as answers come in.

Three parts are moves without a reason, or repeat earlier text:

- "dialogue mapping" is a named method the agent is told to run, but the text never says why;
- the scope paragraph (82-84) repeats the "Where the first release ends" bullet (line 30);
- the pre-mortem paragraph (86-87) repeats "How the user will judge the result" (line 31), and the brief template's
  "How it will be judged" already says "from the pre-mortem, each with its number or shipped example".

**Fix.** Cut the section to the four habits above, each in one sentence with its reason. Keep the Q2 example,
because it carries the "what it commits you to" voice. Delete the dialogue-mapping line and the scope and pre-mortem
paragraphs. Fold "pin each judgement to a number or a shipped example" into the line 31 bullet as part of the
outcome. Gist of the new opening: "How you run the conversation is yours. These habits keep the user's answers quick
and their reasons on record: ..."

**Checked:** against the stage's own "When you're done" and brief template; no CLI involvement.
**Lines:** about 12 to 15 go.

## 3. Builder "Without a lead": a command walk-through that the results' `next` already gives (section)

`builder/SKILL.md:179-191`. Quotes: "After you merge a milestone, run `run --module <M> --worktree . --checks-only`,
which `merge`'s `next` usually gives. ... Its `next` is the `review` command. Run it as given and add nothing", "After
a failed review, `next --module <M> --milestone <id> --worktree .` says whether to carry on ...".

**What's wrong.** This is a sequence of commands, and each one is already named by the previous result's `next`. The
skill even says so at line 21. What the builder needs is the outcome, its mandate, and the one reason it would
otherwise get wrong: leave the review prompt alone, so the reviewer forms its own view.

**Fix.** Rewrite it as goal and mandate. Gist:

> With no lead, the steps the script would take after your merge are yours: follow each result's `next` until a
> review that the `review` command started has judged the milestone, because only that review can set it Done. Pass
> the review command as given, so the reviewer forms its own view. If you can't start one, end with `DONE` and say
> the milestone still needs a review. A planner's task or a decision for the user goes to the user in your reply.

**Checked:** `merge`'s MERGED outside a run names `run --checks-only` in `next` (`agent_loop.py:10724`, COMMAND_HELP
at 15613), and `--checks-only` leads to `review` (15477).
**Lines:** about 8 go.

## 4. Reviewer gives up on a permission it could ask for (opposite failure; small text, high impact)

`reviewer/tasks/milestone.md:46-48`: "If you can't reach the product at all, because the screen is locked, a
permission needs the user's approval or a device isn't connected, judge nothing and end with `BLOCKED needs_access`".

**What's wrong.** Clearing a sandbox refusal is the reviewer's own job. Nothing on the reviewer's side gives it that
mandate. The builder is told "A command that needs more than your sandbox allows, such as a browser, may be allowed
outside it if you ask" (`builder/SKILL.md:80-81`), and the Codex `session_rule` repeats it. The reviewer gets neither:

- `review_prompt` (`agent_loop.py:9237-9254`) never adds `session_rule`;
- `reviewer/SKILL.md` and `reviewer/tasks/*.md` never mention the sandbox (checked by grep).

Elsewhere the set assumes the reviewer asks:

- `proofs.md:137-139`: "so plan for the reviewer to ask";
- the comment in `preflight` (`agent_loop.py`, ~line 6935): "a reviewer that needs one asks for it, and gets it".

As written, a Codex reviewer whose browser is refused by the sandbox can read "a permission needs the user's
approval" as its cue to block. The review then has to be run again later while the user is at the machine, for a
permission that was never needed.

**Fix.** Give the reviewer the mandate, and have the script tell it what it is running in:

- In `milestone.md`, gist: "A command your sandbox refuses, such as a browser, usually runs outside it if you ask
  and say why, so ask before you decide you can't reach the product. Block with `needs_access` only for what needs
  someone at the machine: a locked screen, an operating-system permission, a device."
- Have `review_prompt` add `session_rule(headless, host)`, as the build prompt does, so a Codex reviewer gets the
  sandbox line too.

**Checked:** `review_prompt` code, the saved `review.txt` and `design-review.txt` (neither mentions sandbox or
permission except the line above), and the `preflight` comment.
**Lines:** about 3 change and 1 to 2 are added; the script gains one field in two templates.

## 5. `run` REFUSED with no Builders count: a wrong hand-editing procedure in `why`

`agent_loop.py:8032-8036`: "Write their answers as the Builders, host, Merge and Human decides lines of
ORCHESTRATE.md, commit it on the main branch, and run this again".

**What's wrong.** The `why` gives the lead a procedure, and the procedure is the wrong one:

- Stage 2 already wrote the host, Merge and Human decides lines before planning.
- Stage 3 says to save the count with `settings --set Builders '<their words>' --said '<their words>'`.
- Stage 2 (line 40) notes that `adopt` refuses a changed `ORCHESTRATE.md` once main has one, because the settings
  carry the user's permissions.

So the `why` tells the lead to hand-commit the one file the set protects. It also re-asks questions stage 2 already
settled.

**Fix.** Make the `why` the goal and point at the right command. Gist: "the user hasn't said yet how many builders
may work at once; once they have seen the plan, ask them, and save their words with `settings --set Builders ...
--said ...`". Better still, make `next` that `settings --set` command, with `decides: human` and the existing
`ask`. Trim the ask to the builder count, plus any of host, Merge or Human decides that is still missing from the
settings.

**Checked:** the code at 8030-8040, `settings --set` at 10244-10249 ("records the user's choice, so the lead runs
it"), and the stage 2 and 3 text.

## 6. `model_next`: a mundane rerun sent to the user (opposite failure)

`agent_loop.py:8182-8186`: `decides="human", ask="The builder ran on a different model or effort than the settings
name, usually because the host's own setting won. Run it again as set, or change the settings to what it ran on?"`

**What's wrong.** The settings are already the user's standing choice. Rerunning as set carries that choice out, is
reversible, and costs the user nothing. The lead should own that call. The user only needs asking if the settings
should change. Asking every time spends the user's attention, which 4-build and the lead skill say to spare, and
leaves the module stopped until the user answers.

**Fix.** Make the `next` the rerun as set, `by: lead`, with no `decides: human`, and have the `why` tell the lead to
mention it to the user. Keep `decides: human` only when it repeats, which means the host setting keeps winning and
the settings or the host configuration needs the user. Gist of the `why`: "the session ran on X instead of Y; rerun
as set, and tell the user if it happens again, because then the host's own setting needs changing".

**Checked:** code at 8182-8186.

## 7. Lead stage 3: a sequence of moves around one outcome (section, medium)

`lead/stages/3-before-first-build.md:6-23`. Quotes: "First, show the user what the plan will give them ... In the
same message, show what the planner chose ... Remove the `Proposed:` line from each name the user agrees, and
`adopt` the glossary. Give everything else ... as one `plan --kind change --one-step` task ... Once they agree, save
the number of builders ...".

**What's wrong.** The reasons are good: a misread brief costs one message now and days later; names are cheapest to
change before they spread into code; a correction now costs no review. They are buried in a step order, though, and
the mechanics (remove the `Proposed:` line, `adopt`, the `settings --set` syntax) repeat what the commands' `--help`
and the domain-language skill already cover.

**Fix.** Lead with the outcome and the mandate. Keep the reasons and one sentence on the mechanics. Gist:

> Before any builder starts, get the user's agreement to what the plan will deliver and to every choice made in their
> name: the planner's assumptions, each inspection's reference (with its images), and the proposed glossary names.
> This is the cheapest moment to correct any of them, because no design has been reviewed and nothing is built. How
> you present it is yours; plain lines beat the plan's own words. Agreed names lose their `Proposed:` line; every
> other change goes to one change planner in the user's words, since only a planner edits the plan. Then save the
> builder count they give.

**Checked:** `adopt` and `settings --set` behaviour in `--help`.
**Lines:** about 6 to 8 go.

## 8. Lead stage 2, "The first plan": a command recipe with the goal last (paragraph)

`lead/stages/2-start-planning.md:38-46`. Quote: "Then run `plan --one-step --worktree <repo> --task '<what the user
asked for, in their words>'`, adding 'The project brief is <path>.' when there is one, and 'The user allows up to
<n> builders at once.'".

**What's wrong.** It dictates task boilerplate and the order of commands, and only after that gives the reason
(`--one-step` lets the user correct the plan before review). The brief path is something the script knows, since
`settings` prints it. The planner could be told it without the lead copying a sentence into every first task.

**Fix.** Have `plan` add the brief's path to the planner prompt itself when one exists, as it already does for the
glossary (`{glossary}` in `planner/prompts/plan.md`). Rewrite the paragraph as the goal. Gist: "Get a first plan the
user can correct before anyone reviews it: merge what the planner needs onto main with `adopt`, then `plan
--one-step`, with the task in the user's words and how many builders they expect, so it plans enough side-by-side
work."

**Checked:** `plan.md` template has `{glossary}` but no brief field; whether `plan_prompt` adds the brief elsewhere
was not exhaustively traced. If it already does, just delete the "adding ... brief" clause.
**Lines:** about 4 go.

## 9. Lead SKILL: a restart checklist the script already guards (lines)

`lead/SKILL.md:97-99`: "Read `runs`, `ready` and the result files (each result's `result_file`) before you start
anything again, so you don't start a second run on work one already holds."

**What's wrong.** It lists the reads, and the reason it gives is already enforced. `run` takes a hold and refuses
with `IN_PROGRESS_ELSEWHERE` when another run holds the milestone (`take_hold`, `agent_loop.py:4534`, emit at

**Fix.** Cut it to the goal, one sentence: "When your host restarts, your background commands end with it; find out
what finished and what is still running before you start more." The script catches a double start anyway.

**Checked:** `take_hold` and IN_PROGRESS_ELSEWHERE in code.
**Lines:** about 2 go.

## 10. Lead stage 1, "Check the brief before you show it": steps around a clear outcome (paragraph, small)

`lead/stages/1-interview.md:89-96`. **What's wrong:** the outcome is "the brief survives a cold read by someone
planning from it". The text spells out the route: a subagent, given only the path, then repeat. The one reason worth
keeping is that you're too close to see the gaps, and an unanchored reader is needed.

**Fix.** Cut it to two sentences. Gist: "You're too close to see what the brief leaves out, so have it read cold, by
a fresh subagent given only its path where you have one, as a planner would; settle each question it raises with
the user or mark it yours, until a cold read finds nothing that matters."
**Lines:** about 3 go.

## 13. Reviewer `design.md`, "What to read": First/Then ordering (single lines, optional)

`reviewer/tasks/design.md:9-26` sequences the review ("First read ... Then compare ... Then read each item ... Then
check the design's names"). The content is the right set of questions. Only the forced order is procedure. **Fix:**
drop the "First/Then" framing and state it as what an approved design must survive. Low value; the order is natural
anyway.

## 14. Builder correction prompts ask the builder to undo a field the script owns (have the script do it; small)

Saved prompts `merge-refused-state.txt` and `build-old-branch-note.txt`: "Set the status back to in_progress in
docs/plans/APPLE-TILE/DONE.json, commit that, and run `merge` again. Then end your turn with DONE".

**What's wrong.** The script owns `status` beyond `in_progress`, and it detects this exact case. A step-by-step fix
for the builder spends a turn on bookkeeping. **Fix:** consider having `merge` reset a builder-set `ready_for_review`
to `in_progress` itself during its rebase, and say so in the result. If rewriting the builder's commit is
unwelcome, keep the message, but as a goal: "Only the script sets Ready for Review. Leave M2's status in_progress and
merge again." **Checked:** saved prompts only; the merge code path was not traced.

## Looked at and left alone

These read as procedures but are either outcomes or the CLI contract:

- the builder's "What finished looks like" (outcomes);
- the planner's "When you're done" (outcomes);
- the diagnose `KEEP` routing and the reviewer's repeat-naming rules (the script reads them);
- `needs_rules` and `session_rule` (facts about the session);
- the escalation ladder in `escalation_next` (a deliberate guard that 4-build tells the lead to follow);
- the README walk-through (for people, not agents).

The interview's "ask for a number rather than proposing a default" (1-interview.md:52-54) is a rule, but it gives
its reason, and asking costs little while the user is in the chat.
