# Pattern 7: agent-facing text inside agent_loop.py

Scope: the text the script sends or prints for agents: the prompt-building functions and the templates they fill
(checked against the saved prompts in `tests/orchestration/prompts/`), the `next`/`why`/`message` strings,
`WATCH_WHY`, `COMMAND_HELP`, the top-level `--help` and `CHANGES`. All line numbers are in
`skills/orchestration/lead/scripts/agent_loop.py` unless another file is named. I checked each finding against the
code and, where it applies, against the `--help` output (`python3 .../agent_loop.py <cmd> --help`).

**Failure stories.** No emitted string, prompt template or skill file tells a failure story. I grepped for "Thrum",
"spent N turns", "guessed" and similar, and found none outside comments. The script's ~60 "In Thrum ..." stories are
all in docstrings and `#` comments (for example 6774, 6797-6800, 6895, 6040, 6463), which no agent is sent. They are
maintainer notes and outside this pattern. The one story that does reach an agent is in CHANGES 2.2.1 ("The app refused
that stop before, the script took the turn as stopped, and it worked on with nothing following it"), and it goes when
CHANGES is cut (finding 1).

Rough total that would go: about **330 lines of CHANGES**, about **150-200 lines of COMMAND_HELP and top-level help**,
and about **40 lines' worth of prompt and `why` text**, which is repeated in every prompt a session gets. In all,
roughly 550 lines.

## 1. CHANGES is about 5,000 words of history, and most of it is now wrong or covered elsewhere (6042-6408, ~366 lines)

**What is wrong.** `version_change()` (6425) sends every entry newer than the version this repository last ran. It
sends **all of them** to a repository that has the script's files but no `version.json`, which means one from before
2.1.0. Word counts: 2.9.0 alone is 1,803 words, 2.10.0 is 330, and the whole dict is 5,041. A lead coming up from 2.8
gets about 2,200 words. Most of it:

- **describes behaviour that `--help` and `next` now carry.** For example, 2.10.0's "`ready` and `next` print one
  JSON line ... adopt, migrate, human, merge and main-check keep their own exit statuses", 2.9.0's builder-slot
  ordering, merge-conflict field merging and the quiet window, and 2.4.0's `steps_run` and `stopped_because`. This is
  exactly the "how it works" that the cleanup moved into the CLI.
- **is overtaken by later entries, and now misleads.** 2.2.3 says "Read the build skill again now" (there is no
  build skill). 2.4.0 says "New `watch` ... (3 hours ...)". 2.8.0 says "The human runs `/lead` where they ran
  `/build`". 2.8.3 says the lead's skill "says how to agree a proposed name". 2.2.2 says "You write a planner's task
  yourself". 2.1.0 says "`run` prints REFUSED when as many builders ... Ask the human". A lead reading oldest-to-newest
  meets each old rule before the entry that changes it.
- **uses names the glossary avoids, all through it:** "the human" (16 strings, such as 6208, 6222-6226, 6234-6249,
  6351-6364, 6384), "round" ("counts no round", 2.1.0), "land/lands/landed" (6074, 6124, 6127, 6185, 6293), "claim"
  and "accepted". The 2.9.0 entry that announces the rename to "the user" (6136) is surrounded by older entries still
  saying "the human".
- **contains skill content.** The 2.9.0 entry at 6136-6150 retells the whole interview stage: numbered questions,
  pre-mortem, the subagent read and `Merge: local`. The `stages/` files hold all of this.

**What it should keep.** A lead upgrading needs only what it must *do* or *tell the user*, which neither the current
skill nor `--help` can tell it, because they describe the present rather than the change:

1. **Read the lead skill again** (the 2.10.0 first line; also 2.8.0, since the skill was renamed and moved). One line
   per version whose skills changed.
2. **The script's path moved** (2.8.0: `lead/scripts/agent_loop.py`). One line. `next`/`argv` already name the
   newest copy, so this matters only for a lead's own notes.
3. **Changes the user will notice, or that change a user's decision.** The person is now "the user" (2.9.0, one
   sentence). The lead writes the settings, with `Merge: local`, and asks for a `Builders:` count before the first
   build (2.9.0). A design is approved after two design reviews in a row that ask for changes (2.7.0). Evidence is no
   longer committed, and its links don't open in a fresh clone (2.6.0). The Codex default model changed (2.3.7). The
   daily report is gone (2.4.0).
4. **Steps the lead must take once.** `migrate` (2.2.0, 2.6.0) and `migrate --commit-map` (2.7.1). Even these could
   go, because every command refuses an old project and its message names `migrate` (`old_names_message`, about
   1284, and the 805 message). Keep one line saying "run `migrate` when a command names it".

**Fix.** Rewrite CHANGES to one or two lines per version, each one an action or something to tell the user, in the
glossary's current names. Drop every entry that only describes a fix or a new field: 2.3.x, 2.2.4-2.2.6, 2.8.1, 2.8.2
and most of 2.4.0 and 2.9.0. Collapse everything before 2.6.0 into one line ("From before 2.6.0: read the lead skill
again, and run `migrate` when a command names it"). That comes to about 30-40 lines. Optionally, have
`version_change` send only the versions after the last one seen, which it already does, plus cap a jump of many
versions to the newest entry and the collapsed line. **Checked:** I read `version_change`; it returns the whole slice
`(since, VERSION]`, or everything when `older` is true and `seen` is None.

## 4. `next`/`why` strings repeat the lead skill's judgement on every result

The lead skill and `4-build.md` were cut so that the CLI holds the mechanics and the skill holds the judgement. These
`why` strings put the skill's judgement back into the output:

- **`human_next` suffix, 2744-2746.** Every `decides: human` `why` ends: "Ask the user in chat; once they have
  replied, run the command with their words in --said, as they gave them, and never decide for them". The lead skill
  says this ("put its `ask` to the user ... run its command with their words"; "never save your guess as their
  answer"), and so does the top-level contract. **Fix:** delete the suffix. `decides: human` and `ask` carry it.
- **Needs Context `why`, 2954-2959.** "The builder asked a question. The lead answers it from what it can see ...
  When the question is about the plan ... a planner answers it instead. Take it to the user only when only they can
  decide, together with any other questions for them, while other work carries on." This is `4-build.md`'s
  "Questions" section, restated. **Fix:** "`{mod} {mid}` is Blocked: Needs Context ({what}). Answer it with
  `run --message`, or give it to a planner (`alternative`)."
- **Needs User Feedback `why`, about 2905-2911.** "Their reply goes into the record file, where the builder reads it
  and the reviewer counts it as the user's words ... Don't pass it through `run --message`, because a reviewer can't
  tell those words from an agent's." The skill says the same ("User Feedback and approvals go through `human
  feedback`, because a reviewer only counts the user's words recorded there"). **Fix:** "`{mod} {mid}` is Blocked:
  Needs User Feedback on {items}. Show the user the evidence and ask; `then` resumes the builder."
- **Needs Access/Hardware `why`, 2921-2927.** "The visible run unblocks it; nothing is recorded, and the user isn't
  asked to confirm it." These are internals. **Fix:** "The user has to be at the machine to {kind}; run this while
  they are."
- **`WATCH_WHY`, 15088-15091.** "Read this for delivery problems and act on them: message a builder (stop its run
  with `pause --module <M>`, then start it again with `run --message`), start a planner on a re-plan, change the order
  of the work, start a builder on ready work, or ask the user." This is the list of things the agent can do that the
  user called wasted breath. `4-build.md` already gives the mandate, and says to start `watch` again whenever it ends.
  **Fix:** cut to "Start `watch` again in the background." or delete it.

**Checked:** I read `next_for` (2870-3001), `human_next` and `WATCH_WHY`, and compared them with `lead/SKILL.md` and
`lead/stages/4-build.md`.

## 5. The builder prompt says the same things two or three times, and teaches Codex its own tools

Seen in `build-codex-headless-full.txt` (672 words) and `build-resumed-restatement.txt`.

- **`session_rule` Codex paragraph, 6801-6806.** "Edit files with `apply_patch`, because a text-replacing script
  changes nothing ..." and "keep waiting on it with a long `yield_time_ms`, such as 300000" teach Codex its own tools.
  "A request to run a command outside the sandbox is granted or refused at once, even here; an item is blocked only
  once its own request has been refused" repeats `builder/SKILL.md` ("Each request is decided on its own, so an item
  is blocked only once its own request has been refused"). "Even here" also contradicts the headless sentence just
  before it, which says no approval prompt can appear. The paragraph also starts with `\n\n` inside a bullet list, so
  the saved prompt has a loose paragraph between bullets. **Fix:** keep one bullet: "- On Codex, a browser or another
  windowed program runs only outside the sandbox, so ask for that at the start; `jobs` lists your background jobs
  (the sandbox refuses `ps`)." Delete the rest.
- **Headless `session_rule`, 6820-6823.** "end your turn with `NEEDS_CONTEXT` and the question, or `BLOCKED`, as
  below, and the lead gets it answered" duplicates the template's closing paragraph, which says the same thing in the
  same words. **Fix:** "This session runs in the background, so no approval prompt or question asked through a tool
  reaches anyone."
- **`resources_rule`, 6773-6793.** "Wrap a command that uses one in the script's `lock <name> -- <command>`, which
  waits its turn" repeats the builder skill's "Shared resources" section. The shared-resource sentence teaches `.alone`
  semantics and says "A lock keeps out only runs that take it, so it doesn't make the machine quiet for a timing",
  which is the content of `lock --help`. **Fix:** one bullet with only the facts the skill can't know: "- Exclusive
  resources: {names}. Shared: {name} (up to {n} runs at once; `{name}.alone` takes the whole device). The script stops
  a lock held longer than {limit}."
- **`binding()` restatement, 6905-6909.** It says the status three ways: "with {mid}'s status left as in_progress for
  the script to set. In {done}, change only {mid}'s items' `builder_result` and `evidence`, and its `status` only to
  in_progress." **Fix:** "In {done}, change only {mid}'s items' `builder_result` and `evidence`; the script sets the
  status."
- **`build.md` template, "About this session" bullet 2.** "Once the script's checks pass on your merged work, the
  script starts a reviewer ..." repeats the goal paragraph two lines above ("the script runs the checks on the merged
  work and sets the status itself"). **Fix:** "- A lead is running this build." (The template is in
  `builder/prompts/`, but the script owns it.)
- **Old-branch note, 4866.** "Commits in this worktree ... set {what}, as builders did before 2.1.0." This is a
  history clause in an error. **Fix:** drop "as builders did before 2.1.0". Separately, whether any branch from before
  2.1.0 still exists is a question about the code.

**Checked:** I read all of these and the saved prompts. The loose paragraph is visible in
`build-codex-headless-full.txt`, between the background bullet and the resources bullet.

## 6. The planner and reviewer prompts make the same point twice

- **`scope_text`, 191-201** (90 words), and **`planner/tasks/module.md`**. Both tell a planner limited to one module
  to end with `BLOCKED: needs <MODULE>'s files`, and that the lead then gives the task to a whole-project planner. A
  module task run with `--module` gets both. `scope_text` also buries "which the script refuses" mid-sentence.
  **Fix:** "- This task is limited to {scope}, because planners of other modules may be running: change its folder,
  the files outside the plans folder it owns, and additions to shared project files such as the glossary. If it needs
  another module's files or an interface in the module list, end with `BLOCKED: needs <MODULE>'s files`, saying
  which." Then delete the matching sentence in `tasks/module.md`, or this one.
- **`planner/prompts/plan.md`, "About this session".** "It leaves out the project's test command, and runs each check
  under the item's lock, waiting while a builder holds it" is `check --help` content. "The script lists the files you
  changed itself" is an internal. **Fix:** cut to "`check ... --items-only` tries a milestone's item checks without
  recording anything."
- **`review_notes`, 2373-2375.** "Judge the items before you read any of these, as 'A milestone reviewed before' in
  your instructions describes." `reviewer/tasks/milestone.md`, printed a few paragraphs below in the same prompt, says
  it with the reason. **Fix:** delete the sentence.
- **Design review "round", 8912-8916, and `reviewer/tasks/design.md:54-56`.** The script adds "This is design review
  round N of 2. If it asks for changes, the script approves ... so ask now for everything that has to change." The
  task file says "Put every Must Fix you find in this review, because a design gets only a fixed number of rounds
  ...". Same point twice, and "round" is the glossary's avoided name for one review. **Fix:** keep it in the script
  ("This is design review N of 2 in a row that may ask for changes; after the second, the script approves the
  planner's revision without another review"). Cut the task file to "Put every Must Fix you find in this review." Do
  the same for "design review rounds" in the planner task at 9219 and in the CHANGES 2.10.0 line.
- **`checks_note`, 7648-7651.** "It ran them in its own clean checkout, apart from any that had already passed on
  exactly those files" is an internal. **Fix:** "The script already ran {X} on the files at {sha}, and they passed;
  run one again only if you doubt it."

## 7. The `review --help` has a broken sentence, and the diagnosis rule appears in three helps (15540-15556)

"REVIEWED's `next` is the {command, by, why}." is followed nine lines later by "After a pass it is the next ready
milestone or "finished", the planner's revision with `findings` after DESIGN CHANGES." That sentence lost its subject
when the diagnosis paragraph was put between the two parts. The diagnosis paragraph itself ("A planner given a
diagnosis ends with `PLANNED` ... or `KEEP` ...") repeats `next --help` and run's WAITING entry. **Fix:** join the
two halves of the `next` sentence, and replace the diagnosis paragraph with "`next --help` gives the escalation."
Delete the internal "entries overwritten before reviews were kept say `review_in_history`" as well. **Checked:** this
is visible in `review --help` output.

## 8. Avoided names in the top-level help and the subcommand list

- The usage line and subcommand list print the old aliases: `human (owner)`, `settings (profile)`, `runs (loops)`.
  `owner`, `profile` and `loop` are all on the glossary's Avoid lines. **Fix:** keep the aliases working but hide
  them from help (for example, rewrite `sys.argv[1]` before parsing instead of using `aliases=`). Do the same for
  "(`loops` before 2.1.0, still accepted)" at the start of `runs --help`, "(--budget-hours before 2.2)" and the
  `--owner-rule` alias.
- The help's first sentence says "decides itself which work is accepted", where the glossary's name is "Done".
  **Fix:** "and decides itself which milestones are Done."
- `cleanup` and `adopt` help say "acceptance" and "accepted" (adopt: "no Ready for Review record, review or
  acceptance"; migrate: "Acceptance survives"). **Fix:** use "Done".
