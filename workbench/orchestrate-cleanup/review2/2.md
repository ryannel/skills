# Pattern 2: paths, defaults and setting values written out where the CLI already holds them

Scope: every file in `skills/orchestration/` except `lead/stages/4-build.md` and the code itself. All line numbers
are from the current working tree. "Checked" means I read the code or ran `--help`/`settings --template`.

Overall: the agent-facing strings in `agent_loop.py` are already clean on this point. The prompts fill in real
paths (`{done}`, `{module_dir}`, `{glossary}`, `{captures}`, `{handoff}`, `{graded}`), and `next`/`why` strings use
computed values. What is left falls into three groups:

1. The lead's stage 2 repeats the settings template's own notes on defaults, and works around gaps in that template.
2. The planner and design-review prompts leave out the brief, module-list and plans-folder paths. The skill text
   makes up for it by writing `BRIEF.md in the plans folder` and `ARCHITECTURE.md in the plans folder`.
3. The README writes out thresholds, counts and example model names that the script holds. Two script messages also
   give the wrong way to change a setting.

Roughly 35 to 45 lines of skill and README text would go. The script would gain a few template variables and two
template notes.

---

## 1. `lead/stages/2-start-planning.md` repeats and patches `settings --template` (about 12 lines)

**Where:** lines 11-16 and 27-31.

- 11-12: "Keep the template's `Worktrees:` line, so `run` gives each module its own worktree, and its `Graded
  examples:` line, so the reviews the user overturns teach later reviewers..."
- 14-16: "The script won't read settings with no `Test command:` line, so write `- **Test command:** none  *(the
  planner chooses it)*` until then."
- 27-29: "Leave out each host and model line the user named nothing for. The script then uses the host it runs in
  and each host's own default model ... A project that only uses Claude Code gets `Default host: claude`, so a
  command started from outside Claude Code doesn't fall back to Codex."
- 30-31: "Write `Review host: other` when the user builds with both hosts, because a reviewer from another company
  shares fewer of the builder's blind spots."

**What's wrong:** each of these says what a settings line does, what its default is, or how the default resolves.
The template prints that note beside every line. These sentences exist only because the template prints a misleading
example or leaves part of the default out.

**Checked:** `settings --template`:
- It prints `Test command: npm run check` as a real-looking value, marked "required". Nothing says the lead should
  write `none` until the planner chooses.
- It prints `Worktrees:` and `Graded examples:` marked "optional", so a lead copying the template might drop them.
- The `Default host` note says "left out, the host the script runs inside". It omits the rest of the chain that
  `default_host()` (line 5551) and `settings --help` give: "else the only one installed, else codex". The `<Host>
  model` note already says "only when the user named a model".
- The `Review host` note already gives the reason ("a reviewer from another company shares fewer of its blind
  spots").
- `settings --worktree` already prints `host_when_none_named`.

**Fix: have the script do it, then delete these lines.**
- Template prints `- **Test command:** none  *(the planner chooses it once the stack is chosen; required)*`.
- Template notes on `Worktrees:` and `Graded examples:` say "keep this line" and what it gives.
- The `Default host` note gives the full fallback chain, ending in codex, so the lead can see a Claude-only project
  needs the line.
- Delete 11-12, 14-16, 27-29 and 30-31.

What stays: the judgement on `Merge: local` and AGENTS.md (23-26), and "leave out `Builders:` until they have seen
the plan". The `Builders` line could be one sentence: "Leave out the `Builders:` line until the user has seen the
plan, so nothing builds before they agree."

## 3. Script messages give the wrong way to change a setting (2 strings)

**Where:**
- `agent_loop.py` 12287, `adoptable()`'s refusal for a changed `ORCHESTRATE.md`: "adopt doesn't merge a changed
  settings file on an existing project: the lead commits and merges it with git once the user has agreed to it".
- `agent_loop.py` 576-581, the `next` of `unplanned()`, which `settings` and other commands print on a new
  project: "the lead writes the project settings (ORCHESTRATE.md) from the brief and commits them, then a planner
  writes...". Its command is `plan`, run directly.
- `agent_loop.py` 3419-3423, `hold_limit_note()`, which a builder sees: "ask the planner to raise the `Lock hold
  limit` line in ORCHESTRATE.md."

**What's wrong:** these messages contradict the skill and `settings --set --help`.
- The skill (stage 2, 40-41) changes a line with `settings --set` and the user's words, and merges a first
  `ORCHESTRATE.md` with `adopt`.
- A lead that follows the adopt refusal hand-commits settings without the `--said` trail.
- The unplanned `next` skips `adopt`.
- A builder has no channel to "ask the planner". The hold limit is a settings line, so changing it is the lead's
  job, with the user's word.

**Checked:** read all three in the code. `settings --help` says `--set` "refuses inside a session the script
started" and keeps the user's words in the commit.

**Fix: rewrite the strings in the script.**
- Adopt refusal: "change a line with `settings --set LABEL VALUE --said '<the user's words>'`", as a `next` with
  `decides: human`.
- Unplanned `why`: "write ORCHESTRATE.md from `settings --template` and merge it with `adopt`, then plan".
- Hold-limit note: "if the work really needs longer, say so in your report or end BLOCKED; the lead can raise the
  `Lock hold limit` line".

## 4. README writes out escalation counts, cleanup thresholds and timings held by the script (about 15 lines)

**Where:** `README.md`
- 129-140: the escalation table, "the fourth failed review with a repeated finding; or the sixth in all", "The third
  failed review, or the third with a repeated finding", "the first, second, fourth or fifth". This is right after
  line 131: "`next --help` gives the exact counts."
- 87-88: "When the second review in a row also asks for changes ... without a third review".
- 156-157: "`watch`, which ends every few hours, and sooner on a warning sign such as a builder with no progress for
  two hours."
- 244-246: "any nobody has used for six hours, or for half an hour when the disk has less than 30 GB free."
- 248: "Claude Code deletes its session files after 30 days".

**What's wrong:** these are constants in the script: `NEW_SESSION_AFTER_FAILED_REVIEWS = 3`,
`REPEATS_TO_DIAGNOSE = 4`, `FAILED_REVIEWS_TO_DIAGNOSE = 6`, `DESIGN_REVIEW_ROUNDS = 2`,
`LEAD_CHECK_IN_S = 3h` (and the `Lead check-in` setting), `NO_PROGRESS_WARN_H = 2`, `TREE_IDLE_S = 6h`,
`TREE_IDLE_LOW_DISK_S = 30m` and `LOW_DISK_BYTES = 30 GB`. The README itself (412-414) says that copying these
"left some copy wrong" after every change. The escalation table contradicts its own pointer.

**Checked:**
- `next --help` gives 3, 4 and 6.
- `watch --help` gives 3 hours, 2 hours and 5 minutes.
- `cleanup --help` does not give the 6h/30 min/30 GB rule. That rule lives only in the README and in the changelog
  text at line 6315.

**Fix:**
- Keep the escalation table's order and outcomes, and drop the numbers: "after repeated failures", "after more
  failures", leaving `next --help` for the counts.
- Cut 87-88 to "after a set number of rounds asking for changes, the script approves the planner's revision without
  another review".
- Cut 156-157 to "by `watch`, at the lead check-in or a warning sign".
- Move the checkout-idle rule into `cleanup --help` (formatted from the constants). The README then says "the script
  removes idle checkouts itself; `cleanup --help` says when."
- 248 is the host's behaviour, not the script's. Keeping it is fine for people, but it will drift.

## 8. `COMMAND_HELP` writes numbers as literals that the code holds as constants (no skill lines, but a drift source)

**Where:** `agent_loop.py` `COMMAND_HELP` (line 15401 on):
- `next`'s help: "4 reviews with a repeat, or 6 failed reviews", "3 failed reviews".
- `watch`'s help: "3 hours by default", "no progress for 2 hours", "for 5 minutes", "a planner queued for an hour".

**What's wrong:** `--help` is the right home for these numbers. But they are typed in by hand beside the constants
they describe (`REPEATS_TO_DIAGNOSE`, `FAILED_REVIEWS_TO_DIAGNOSE`, `NEW_SESSION_AFTER_FAILED_REVIEWS`,
`LEAD_CHECK_IN_S`, `NO_PROGRESS_WARN_H`, `READY_IDLE_WARN_S`, `PLANNER_QUEUE_WARN_S`). Changing one constant leaves
the help wrong. This is the same failure the cleanup was meant to remove. The changelog at line 6083 shows these
values do change: "warns about idle ready work after 5 minutes rather than 30".

**Checked:** grep found no formatting of `COMMAND_HELP` from these constants. It is a plain dict of strings.

**Fix: have the script do it.** Build those help lines with f-strings from the constants, as the prompt functions
already do (for example, `resources_rule()` uses `limit_text(prof['lock_hold_limit_s'])`).
