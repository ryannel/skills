## F1. builder/SKILL.md, "Without a lead" (L179-191): 13 lines down to 3

Quote: "After you merge a milestone, run `run --module <M> --worktree . --checks-only`, which `merge`'s `next`
usually gives. It starts no agent, and sets the milestone Ready for Review once the checks pass. Its `next` is the
`review` command." ... "After a failed review, `next --module <M> --milestone <id> --worktree .` says whether to
carry on in this session, hand over to a new one, or send the milestone to a planner."

What's wrong: it walks the command chain step by step, and every step is already in the output. `merge --help`: "a
MERGED outside a run names `run --checks-only` in `next`". `run --help` describes `--checks-only` ("For a builder in
a chat with no lead, after it merges") and says READY_FOR_REVIEW's `next` is the review command. `next --help` lists
same_builder, new_builder_session and diagnosis, and its result carries `action`, `message` and `next`.

Fix: keep the mandate and the one judgement. Gist: "In a chat with no lead, you carry the milestone through the
script's checks and its review yourself: follow each result's `next`, starting from `merge`. Run the review exactly
as given and add nothing, so the reviewer forms its own view. A planner's task or a decision for the user goes to
the user in your reply. If you can't start a review, end with `DONE` and say the milestone still needs one."

Checked: `merge`, `run`, `next` `--help`. Covered.

## F2. builder/SKILL.md, "Shared resources and long commands" (L143-155): 13 lines down to 3

Quote: "Wrap a command that uses one in `lock <name> -- <command>` ... `locks` shows who holds each lock ... Start it
with `background -- <command>` and wait for it with `wait <id>`. The job carries on when your turn ends, and the
next turn's prompt names it."

What's wrong: this is said three times over. The build prompt's `resources_rule()` names this project's resources
and gives the `lock <name> -- <command>` and `<name>.alone` syntax, and the hold limit. `lock --help` has the syntax
and the hold limit. `background --help` says "Use it for anything longer than a few minutes ... because a host stops
a tool call that runs too long". The new-session and turn-limit notes (`build-new-session-note.txt`,
`build-resumed-after-turn-limit.txt`) name the running jobs and give the `wait` command. The skill also says the
resources are in "your prompt", which shows the prompt is the source.

Fix: keep only the judgement the CLI can't give. Gist: "Hold a lock only for the command that needs the resource,
and before taking one for a run that needs the user or the screen, check the user is there and the screen is
unlocked. A busy resource is normal: do other work meanwhile, and end `BLOCKED` only if the holder seems stuck. Run
anything longer than a few minutes with `background`." Delete the syntax and the sentence on the next turn's prompt.

Checked: `lock`, `locks`, `background`, `wait` `--help`; `resources_rule()` at agent_loop.py L6773; saved prompts.
Covered.

## F3. builder/SKILL.md, "Merging" (L132-141): 10 lines down to 3

Quote: "`merge --worktree .` rebases your branch onto the main branch, runs the test command, and merges. ... When
several builders merge at once, `merge` tests them as one batch, so it can take a while." and "When it says the main
branch fails without your branch, write your handoff and end with `BLOCKED main_broken:` and what it names".

What's wrong: `merge --help` describes the rebase, the test command, batching and bisection. The main-broken case is
already handled in the output: `main_broken_result()` (L11178) prints in `detail` "Stop, and end your turn with
`BLOCKED main_broken: <this commit and the test that fails>`; the lead gives the fix to whoever owns it". The same
ending is also listed in "What finished looks like" item 4.

Fix: keep the reason merge is the only route. "Bring work into the main branch only with `merge`, because every
other builder's worktree is built on that branch's history. A `FAILED` result's `detail` says what to do." The batch
sentence can go into `background --help`'s existing advice to run a long merge in the background, which it already
covers ("a merge").

Checked: `merge --help`; `main_broken_result()` text. Covered.

## F4. lead/stages/2-start-planning.md: script behaviour the help and template already give, plus two jobs the script should do

**a. Restating `plan` and `adopt` help (L38-46).** Quote: "The planner works in the script's own checkout of the
main branch's tip, so it sees only what is merged there. ... `adopt` merges a first `ORCHESTRATE.md`, but once the
main branch has one it refuses a changed copy, because the settings carry the user's permissions." and "`--one-step`
stops before the design reviews". `plan --help` says the planner runs in the script's checkout of the tip, and
`--one-step` is described there. `adopt --help` says it merges a first ORCHESTRATE.md and refuses a changed one "the
lead commits it once the user agrees". Fix: cut to the goal: "Merge the brief, glossary and settings with `adopt`,
then start the first plan with `plan --one-step` and the user's words as the task, so the user can correct the plan
before anyone reviews it."

**b. The script should catch unmerged plan files (have the script do it).** The text has to warn the lead to
`adopt` first because `plan` doesn't check. `run` and `ready` already return `unmerged_plans` with `next` = `adopt`
(`drift_fields()`, L3235), but `cmd_plan` (L9506) never calls it, so a brief left uncommitted is silently not seen
by the planner. Fix: give `plan` the same check `run` has, returning `unmerged_plans` and `next: adopt` with the plan
command under `then`. Then the adopt sentence above can go too.

**c. The script should name the brief in the planner's prompt (have the script do it).** Quote (L43-45): "adding
'The project brief is <path>.' when there is one". The script knows the path (the settings' `Purpose` line, and
`settings` prints it), but `PLAN_TEMPLATE.format` (L9623) passes only the glossary. Fix: add "The project brief is
{brief}" to `plan.md`'s "About this session", and cut the instruction. The builders count still has to come from the
lead on a first plan, because there is no `Builders:` line yet; keep that half.

**d. Template notes restated (L11-12, L14-16, L30-31, L33-34).** Quotes: "Keep the template's `Worktrees:` line, so
`run` gives each module its own worktree, and its `Graded examples:` line, so the reviews the user overturns teach
later reviewers how strict they are"; "The script won't read settings with no `Test command:` line, so write ...
none"; "`Review host: other` ... because a reviewer from another company shares fewer of the builder's blind
spots"; "`run` starts no builder until it has a count". `settings --template` already gives each of these reasons
in the line's note (Worktrees, Graded examples, Test command "required ... or `none`", Review host "a reviewer from
another company shares fewer of its blind spots", Builders "`run` starts no builder without a count"). Fix: cut each
to the decision: keep the Worktrees and Graded examples lines; Test command `none` until the planner chooses one;
`Review host: other` when the user builds with both hosts; leave out Builders until the user has seen the plan. If
you want the "(the planner chooses it)" wording, put it in the template's Test command note.

**e. Duplicate of 4-build (L54-56).** "Save it with `settings --set`, with the user's words in `--said`." The same
instruction is in 4-build L11-12, and `settings --help` covers `--said`. Fix: cut to "that is a settings line; save
it with `settings --set`", or delete it and rely on 4-build.

Checked: `plan`, `adopt`, `settings` `--help`, `settings --template`, `cmd_plan` and `drift_fields` code.

## F5. lead/SKILL.md, the result contract and newer-copy handling (L34-42): 9 lines down to 3

Quote: "A result that stops short of what you asked for carries `next`, the command for the step that comes next,
with `why`. ... When `next` says `decides: human`, put its `ask` to the user in the chat, and once they reply, run
its command with their words in place of the placeholder." and "When a result's `warnings` say a newer copy of the
script is installed, read this skill again from the newer copy before the next command, because commands change
between versions."

What's wrong: `agent_loop.py --help` ("Results and exit status") defines `next`, `argv`, `by`, `why`,
`decides: human` and `ask`, and 4-build L47 says to follow `next` and put `ask` to the user. The newer-copy warning
from `emit()` (L6608) already says "run the next command from that copy, and read the lead skill again, because its
commands may have changed".

Fix: keep the judgement and the one rule the CLI can't enforce. Gist: "`next` is usually right, so run it unless
you can see a reason it isn't. Let each command's output and exit status reach you, because a refused command line
looks like success once its error is thrown away. When a result carries `changed`, tell the user the parts that
affect them." Delete the newer-copy sentence.

Checked: `agent_loop.py --help`; the warning text in `emit()`. Covered.
