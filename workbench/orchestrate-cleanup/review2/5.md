# Pattern 5: false or stale claims

Scope: every skill file, README.md, GLOSSARY.md, the prompt templates and saved prompts, every `--help`
(captured with `agent_loop.py <command> --help`), and the agent-facing strings in `agent_loop.py`
(`session_rule`, `needs_rules`, `resources_rule`, `binding`, `browser_warnings`, results' `next`/`why`).
`lead/stages/4-build.md` was skipped as the brief said. Nothing in the repository was edited.

This pattern produces few whole-section cuts. Most findings are one or two lines that say the wrong thing, and
the fix is a rewrite, not a deletion. They are ranked by how much harm the false claim does, not by how many
lines it takes up.

Line numbers are for the working tree as of this review.

---

## 1. The options pick does not close without a reviewer, though three files say it does

- `planner/references/proofs.md:158-160`: "The user has judged the pick, so it closes without a reviewer once
  its checks pass. End the module's planned stretch at the pick, and name the milestones after it in the plan
  file without items"
- `planner/SKILL.md:117-118`: "A reviewer reads a milestone only if it has an `inspect` or an `ask`, or is the
  last of the module or of the stretch you planned, unless the stretch ends on an item the user judges."
- `README.md:111-114`: "A stretch that ends on your own judgement, such as your pick between options, has had its
  judge."

**What's wrong.** `needs_review()` (agent_loop.py:1763-1773) returns True before it looks at the user exception
whenever `milestone["id"] == done["milestones"][-1]["id"]`, meaning the done-when file's last milestone. The same
docs tell the planner to put the milestones after the pick in `PLAN.md` as headings with no items. A done-when
milestone with no items is refused (`"{mid}: no items"`, line 1383). So in a real plan the pick is always the
done-when file's last milestone, and it always gets a reviewer. `plan_ahead` also waits for the pick before it
plans the next stretch (line 3108), so the pick never stops being the last milestone. The unit test that covers
this case (`tests/orchestration/test_agent_loop.py:1399`) only passes because it uses a done-when doc with an
item-less `{"id": "M2"}` after the pick, a file the loader would reject.

**Fix.** Settle which one is meant. If the docs are right, which the docstring's intent suggests, the script
should count a module as finished from the plan file and not from the done-when file's last entry. That is a
code change, so it goes to whoever owns the script. If the code is right, cut the clause in all three places:
- in proofs.md, delete "The user has judged the pick, so it closes without a reviewer once its checks pass.";
- in planner SKILL, end the sentence at "the stretch you planned";
- in the README, delete the sentence that starts "A stretch that ends on your own judgement".

**Checked:** read `needs_review`, `asks_the_user`, `plan_ahead` and the item validation in the code, and the test
fixture.

## 2. Stage 2 says the script follows each host's default model, but it pins its own

- `lead/stages/2-start-planning.md:27-28`: "Leave out each host and model line the user named nothing for. The
  script then uses the host it runs in and each host's own default model, which stays current when a newer model
  ships."

**What's wrong.** With no model line, `resolve()` (line 6677) takes `prof["models"][host]`, which defaults to
`DEFAULT_MODELS = {"codex": "gpt-6.2-sol", "claude": "claude-opus-5-5"}` (line 117). It then passes that model on
the command line (`--model`, line 5576; `-m`, line 585). The model changes only when the script itself is updated.
The README says the opposite of stage 2 and matches the code: "Every agent is started with its model and effort
named on the command line, because defaults change between releases" (README:266-267).

**Fix.** Rewrite it as: "Leave out each host and model line the user named nothing for, so the script's own
current defaults apply, which `settings` shows."

**Checked:** read `DEFAULT_MODELS`, `profile()` lines 429-450, `resolve()` and `host_command()`.

## 4. Which settings lines are required, and who changes `ORCHESTRATE.md`

- `lead/stages/2-start-planning.md:15-16`: "The script won't read settings with no `Test command:` line, so write
  `- **Test command:** none  *(the planner chooses it)*` until then."
- `adopt --help`: refuses "a changed ORCHESTRATE.md the tip already has (the lead commits it once the user agrees)"

**What's wrong.**
- On the first claim: `cmd_plan` reads the settings with `profile(worktree, missing_ok=True)`, and its comment
  says "the settings may still lack the test command a first plan adds" (line 9509). A missing required line is
  only a warning unless the command is strict, and `settings --template` says only that "the commands that build,
  review or merge refuse to run without them". So `plan` reads these settings. Writing `none` also clashes with
  `planner/tasks/project.md:43-45`, which tells the planner to *add* the `Test command:` line.
- On the second claim: the lead doesn't commit settings changes. Stage 2 (line 41) and the lead skill send every
  settings change through `settings --set`.

**Fix.**
- Stage 2: cut it to "Leave the test and setup commands to the planner, which chooses them once it has chosen how
  the project is built; `run` and `merge` refuse to start until it has." Or keep the `none` line and change
  project.md from "add two lines" to "fill in".
- `adopt --help`: change the parenthesis to "(change a line with `settings --set` once the user agrees)".

**Checked:** read `profile()` (lines 387-512), `cmd_plan` line 9509, and the `settings` and `adopt` help.

## 5. `review --help` leaves out BLOCKED, and the glossary misstates what a reviewer's BLOCKED does

- `review --help`: "REVIEWED, INVALID (nothing merged), or the host's HOST_FAILED, SCRIPT_FAILED,
  WRONG_MODEL_OR_EFFORT or PAUSED."
- `GLOSSARY.md:350`, Needs Access row: "A builder or a reviewer couldn't get a permission ... | `needs_access`; a
  reviewer's `BLOCKED needs_access` ending"

**What's wrong.**
- `review` does print `BLOCKED` with `reason: needs_access` (line 8972), and its `next` is the same review under
  `ORCHESTRATE_VISIBLE=1`. The reviewer skill (`reviewer/tasks/milestone.md:47-48`) relies on that, but the
  command's help never names the result.
- After that BLOCKED, the code leaves the milestone "still Ready for Review" (line 8969). It is not Blocked: Needs
  Access, so the glossary row puts a reviewer's ending under a status the milestone never takes.

**Fix.**
- Add to `review --help`: "BLOCKED (`reason` needs_access: the reviewer couldn't reach the product; nothing
  merged, no review counted, the milestone stays Ready for Review, and `next` is the same review in a visible
  session)".
- In the glossary row, drop "a reviewer's `BLOCKED needs_access` ending" and keep the builder's meaning.

**Checked:** read `cmd_review`, lines 8963-8980.

## 6. Planners can run side by side, though `plan --help` says only one runs per repository

- `plan --help`: "One planner runs per repository at a time: another waits for it"
- `run --help` (and `plan --help`), last paragraph: "Run locks (run-<MODULE>.lock, run-_plan.lock)"
- `plan --help`, `--one-step`: "Without it, plan carries on into the design review of each module it left owed
  one, and one planner revision if a design review asks for changes"

**What's wrong.**
- The `--module` flag's own help says a scoped planner "runs beside planners of other modules". `plan_lock()` and
  `plans_clash()` (lines 4130-4158) let module-scoped planners run at once. Only an unscoped planner runs alone.
  The lock files include `run-_plan.<MODULE>.lock`.
- The routine-steps paragraph of the same help says "a planner revision each time a design review asks for
  changes". With `DESIGN_REVIEW_ROUNDS = 2` that can be two revisions, not one.

**Fix.**
- Change it to: "A planner with no `--module` runs alone; planners limited to different modules run side by side.
  A planner whose scope clashes waits ..."
- Add `run-_plan.<MODULE>.lock` to the lock list.
- In `--one-step`, change "and one planner revision if" to "and a planner revision each time".

**Checked:** read `plan_lock`, `plans_clash`, `take_plan_lock`, `DESIGN_REVIEW_ROUNDS` (line 2016), and the
step loop at line 14847.

## 7. The run help's DESIGN_NOT_APPROVED entry describes only `--one-step`

- `run --help`, DESIGN_NOT_APPROVED: "on DESIGN OK goes on to build; any other outcome stops here with the
  review's result under `design_review`."

**What's wrong.** The routine-steps paragraph of the same help says a `run` without `--one-step` goes on to "a
planner revision each time the design review asks for changes, then the run again". So DESIGN CHANGES doesn't
stop a normal run.

**Fix.** Change it to: "on DESIGN OK goes on to build; with `--one-step`, any other outcome stops here with the
review's result under `design_review` (without it, see Routine steps)."

**Checked:** compared with the Routine steps text and `DESIGN_REVIEW_ROUNDS` handling at line 14847.

## 8. Every builder is told a reviewer will judge its milestone

- `builder/prompts/build.md:7`: "Once the script's checks pass on your merged work, the script starts a reviewer
  in a new session to judge the milestone." This line is in every saved build prompt.
- `builder/SKILL.md:15-16`: "A reviewer is a new agent that judges your milestone once you finish."

**What's wrong.** `needs_review()` sends a milestone with only `check` items, which isn't the last of its module
or stretch, straight to Done (`READY_FOR_REVIEW` with `review: false`, as the `run --help` and glossary say). The
template is static, so builders of those milestones are told something false.

**Fix.** Build prompt: "Once the script's checks pass on your merged work, it sets the milestone Done, or starts a
reviewer in a new session when the milestone needs one." Builder SKILL: "A reviewer is a new agent that judges
the milestone, when it needs one, once you finish."

**Checked:** `needs_review` and the `run --help` READY_FOR_REVIEW entry.

script change; the strings stay as they are.

**Checked:** read `session_rule`, its one caller (line 6853), `ALLOWED` and `browser_warnings`.

## 11. GLOSSARY.md is installed with the plugin

- `GLOSSARY.md:9-10`: "This file is for the people and agents who write the set, and it is not installed with
  the skills."

**What's wrong.** Every plugin in `.claude-plugin/marketplace.json` has `"source": "./"`, so an install copies
the whole repository. The glossary is in every installed copy, for example
`~/.claude/plugins/cache/ryannel-skills/orchestrate/2.8.1/skills/orchestration/GLOSSARY.md`. What is true is that
no skill folder holds it and no skill points agents at it.

**Fix.** Change it to: "This file is for the people and agents who write the set; the skills don't read it."

**Checked:** marketplace.json `source` fields, and `find ~/.claude/plugins -name GLOSSARY.md`.

## 12. `review --help` says evidence merges, but it stays in the working folder

- `review --help`: "Captures go in the folder beside the review file (<evidence>/<MODULE>/<milestone>-review/),
  which merges with it." Also "the script merges the review itself".

**What's wrong.** Since 2.6.0 the review and its captures live in the working folder, outside git. The review
prompt says "The review and that folder are in the working folder, which git ignores, and the script keeps them
there", and `adopt --help` says "Evidence ... is never merged". The commit `review` makes holds the done-when
verdicts and the record (line 9122), not the review file.

**Fix.** Change it to: "Captures go in the folder beside the review file (...), in the working folder. If all
holds, the script merges the verdicts and the record".

**Checked:** read `cmd_review`'s change function (lines 9040-9122), the review template and the adopt help.
