**Astra — holistic publication review, 9 November 2026**

**Verdict: changes requested before installing this as the owner's unattended build system.** The three sets have a sound common direction: give capable models outcomes and necessary context, retain requirements, keep state in files, verify claims mechanically, and use independent review where judgement is needed. The remaining problems are principally at the seams between that advice, the loop and the installer. Two reproduced failures lose the substance of the task: planning can report success without producing a plan, and fresh retries lose conversational restrictions. The suite also contradicts its own bounded-continuation and review-filter guidance. These need repairs, not another large rewrite of the skills.

The always-loaded footprint is reasonable on a clean installation. The owner's existing installation is a different case: the installer leaves duplicate skills and the earlier hook for manual removal. The action-time footprint can also be reduced, especially instructing-agents' root document. “The first check is enough” does not make the rest of a skill disappear when the host loads its full body.

**What should stay**

The revised distinction between invented procedure and required task context is valuable. The warning against trusting an agent's retrospective as causal proof is also right. Host facts are dated, uncertainties are often explicit, and the corrected Sol/Astra finding-count comparison no longer pretends to measure recall. The role boundary between instructing-agents and skill-creator is clear. Skill-creator's baseline isolation, outcome grading, receiver tests and context-state records are materially stronger than merely grading attractive prompts.

Orchestrate's durable acceptance record, pinned definitions, dependency queue, clean-checkout verification, fresh review sessions, requested-versus-observed launch fields, and explicit integration permission are useful mechanisms. They should survive any trimming. The README is commendably candid that this version has not completed a real milestone cycle and that check commands are not a security sandbox (`skills/orchestration/README.md:94–122`).

Current vendor guidance supports that direction, with qualifications. OpenAI recommends narrow skill triggers, minimal routers and contextual references; its advice about removing scaffolding is explicitly model-sensitive, not a prohibition on all procedure ([Rethinking skills and prompts for GPT-6 Astra](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)). Anthropic recommends explicit outcomes and constraints, and still supports steps when order **or completeness** matters ([Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)). Opus 5.5 guidance specifically addresses progress-only turn endings, bounded continuation and waiting for outstanding work; medium is its starting effort, with calibration on actual tasks ([Prompting Claude Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5)).

**Ranked findings**

1. **High — Verified: the planner treats a progress report as finished work and can publish an empty success.** `skills/orchestration/build/scripts/agent_loop.py:2365–2367` calls `one_session` with `lambda msg: bool(msg.strip())` and `max_turns=1`. It then validates changed done-when files, but does not require the requested deliverables to exist (`2377–2398`), and emits `PLANNED`, `landed=True` even when `modules=[]` (`2440`). In the existing temporary-repository test fixture, I replaced only `run_turn` with a fake successful turn saying “I will write PAY next.” No planning files were produced. The actual `cmd_plan` returned `PLANNED`, `landed: true`, `modules: []`, `design_review_owed: []`. This is exactly the Opus 5.5 progress-ending failure the companion skill warns about. It also risks integrating partially written plans when the first turn leaves some files. Require an observable planning completion contract, validate the requested artifacts, and distinguish a progress ending or blocker from completion. A short bounded continuation should name the missing result. Do not make a final-line token alone the oracle.

2. **High — Verified: the documented route for owner restrictions loses them on a fresh retry.** `skills/orchestration/build/SKILL.md:19–22` tells the lead to pass a conversation-only restriction through `--message`. `agent_loop.py:2057–2064` consumes that value once; `2013–2015` discards session state on `--fresh`; `binding()` at `1426–1447` does not contain conversation constraints. A fixture run with `--message 'Owner boundary: never edit the schema.'`, followed by `--fresh` without resupplying it, produced prompts containing the boundary `[True, False]`. This is not hypothetical compaction loss. The escalation ladder explicitly requires fresh sessions (`build/SKILL.md:118–120`). Persist owner restrictions in a defined, scoped source that survives both new leads and fresh builders, and make launch/restatement read it. Keep review findings separate so replacing a findings message cannot replace permissions. `workbench/fold-learnings-2026-11-09/RESULT-B.md:42–44` already acknowledges the omission; limiting that commission did not make the release requirement go away. **Suspected additional exposure:** suppressing restatement whenever any Codex goal is active (`2065–2068`) assumes that goal contains all binding restrictions; the code checks status, not objective coverage.

3. **High — Verified: builders have no short limit on progress-only continuations, contrary to the shared guidance.** `skills/instructing-agents/references/hosts-and-models.md:105–108` recommends naming open items and continuing at most two or three times. In `agent_loop.py:2044–2167`, only failed process turns, repeated DONE claims and specific blocker reports have small counters. An ordinary progress-only reply gets “Continue the objective.” and can repeat until four hours without qualifying progress; commits outside the plans folder reset that clock (`387–398`, `2107–2110`). There is no total bound on those cycles. I supplied five unchanged progress-only fake turns: the loop requested a sixth, which I stopped with the fake exit code 130. For Opus 5.5, add the bounded continuation policy the guidance describes, with the outstanding items in the nudge; distinguish useful work from repeated reports. If a longer policy is intentional, document its evidence and reconcile the companion skill. A four-hour inactivity timer is not the same control as a continuation limit. This finding is about stalled continuation, not imposing a new arbitrary deadline on productive builds.

4. **Medium — Verified: an existing marketplace registration can make installation ignore this checkout or `--source`.** `install.py:89–98` checks only whether the marketplace name appears in list output. If it does, Claude updates that registration and installs from it; it never compares its source with the requested one. Codex likewise skips marketplace add at `108–114`. A mocked Claude command trace with an existing `ryannel-skills` at `/old/checkout` and requested source `/new/integrate/checkout` contained only list, update-by-name and install-by-name; the requested source never appeared. This matters directly when switching from earlier worktrees to the publication checkout: a successful invocation can install the wrong revision. Reconcile the registered source and scope, or fail clearly on a mismatch; report the installed source/revision. Updating an old registration is not equivalent to installing the repo the command was run from.

5. **Medium — Verified contradiction; suspected review churn: the automated reviewer fails defects it explicitly considers immaterial.** `skills/instructing-agents/references/kinds.md:109–121` distinguishes a human-facing findings list from a loop that must act on every finding, and recommends merge-blocking findings for the latter. Yet `skills/orchestration/review-milestone/SKILL.md:30–31` requires a fail even if the reviewer thinks a defect does not matter. Lines `57–59` make outside-item defects fail the milestone too; `agent_loop.py:194–198` tells the builder every finding counts. Low-consequence findings can therefore consume retries, trigger a re-plan or park an otherwise acceptable milestone. Reporting all findings is compatible with having a defined acceptance threshold. Keep unmet requirements blocking, separate advisory findings, and state how outside-item problems become blockers. The Claude leniency rationale at `26–28` is also inherited from older-model evidence without its date in this shared skill; it should not masquerade as a measured Opus 5.5/Sol result. The README's qualification does not travel automatically into the reviewer's context.

6. **Medium — Verified: plugin installation and runtime discovery disagree.** The installer installs Claude agents through the plugin (`install.py:83–99`, `README.md:146`), but `agent_installed()` only checks two standalone `.claude/agents` paths (`agent_loop.py:1219–1221`). Thus a clean plugin-only install never receives the intended `--agent` selection at `1259–1261`; `CLAUDE_CONFIG_DIR` is also ignored there. Skill preflight misses this repo's nested Claude plugin layout because its glob requires `skills/<name>/SKILL.md`, whereas orchestrate lives at `skills/orchestration/<name>/SKILL.md` (`1497–1499`); Codex preflight does not inspect plugin skills at all (`1502–1506`). These produce false loader warnings and silently change which agent configuration runs. The prompt's absolute skill path and `--disallowedTools Agent` limit the damage, so this is not a claim that all reviews fail to run. Resolve components through the host registry or one tested installation-aware resolver. Current Claude docs confirm plugin agents are usable with `--agent` ([Custom subagents](https://code.claude.com/docs/en/sub-agents#invoke-subagents-explicitly)). **Suspected separate packaging problem:** `workbench/fold-learnings-2026-11-09/RESULT-D.md:153–157` reports `Agents (0)` after installation despite two declared files. That was left unresolved; I did not re-install into user settings to investigate it.
